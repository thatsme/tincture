# 0.5.0 — stream compression

Status, 2026-11-09: **planned; stage 1 in progress.** The plan was measured
against `v0.4.0` (`1f4c344`) and accepted on 2026-11-06. The defect it found
in encrypted output shipped alone as 0.4.1 (`d908aa4`), and 0.5.0 builds on
0.4.1. Section H gives the order of work and what each stage ends with.

Facts about the code are given as `file:line` at the commit the passage
names. A line reference that names no commit is at `d908aa4`
(`v0.4.1^{commit}`). Measurements name the commit they were taken on; those
taken on `1f4c344` hold for `d908aa4` too, because 0.4.1 changed only
encrypted output and every committed example is unencrypted and
byte-identical between the two.

0.5.0 is ROADMAP item 4a: every stream Tincture writes is Flate-compressed,
except the XMP metadata, with an export option that turns compression off.

## Scope

- **In:** 4a, stream compression, and the export option `compress:`.
- **Out, for later releases:** 4b (object streams and cross-reference
  streams, PDF 1.5) and 4c (linearisation). Both rewrite the file's byte
  layout and collide with signing; 4a changes only what lies between
  `stream` and `endstream`, and each stream's dictionary.
- **Out:** the streaming export (ROADMAP section 8). Section F gives the
  memory figures it needs; compression does not change them.

Three stages, each reviewed and merged on its own (section H):

1. **The decoding test helper, and every test that reads the file's bytes
   moved onto it.** No `lib/` change; proven against 0.4.1's bytes.
2. **Compression itself:** the writers, `compress: false`, the hash and size
   locks re-pinned, the zlib canary, a committed example with an image, the
   examples' self-checks reading inflated text, and the decision on unknown
   options in the other public functions.
3. **Documentation and release preparation.**

## Sources and how they are cited

- **ISO 32000-1:2008** is quoted verbatim from Adobe's free copy,
  `https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf`,
  with its clause. A passage quoted from it is cited as **quoted**.
- **veraPDF rules** are cited as `<profile> <clause>-<test>`, from the profile
  XML shipped in veraPDF 1.30.2, the version CI runs.
- **ISO 19005-2** itself was not available. Where the profiles are silent,
  this document says so and does not quote the standard.

Measured on the 14 committed example PDFs at `1f4c344`, labelling each
stream by the object that refers to it. Shares are of the stream bytes as
stored in the file.

|---|---|---|---|---|---|

| form XObject (public) | `serialize.ex:1942-1950`, `form_xobject/2` | none | **FlateDecode** | 3/14 | 0.03% |
| widget appearance (`/AP` `/N`, `/D`, states) | `form_xobject/2` | none | **FlateDecode** | 5/14 | 0.20% |

| XMP metadata | `serialize.ex:417` | none | **none (left unfiltered)** | 13/14 | 0.38% |

- **No other kind of stream exists.** Every stream writer returns
  `{:stream, head, data}` since 0.4.1, and these are all of them.
- **The font programs are the size.** `FontFile2` is 90.67% of the stream
  bytes in the examples, and 78.9%–97.7% of each example.
- **No committed example contains an image**, so image streams and soft
  masks run through no validated claim and no regenerated-examples check.
  0.5.0 does not change image streams, but its veraPDF evidence says nothing
  about them until an example draws one. Stage 2 adds that example.

### The XMP stays unfiltered

**Decision.** ISO 32000-1 14.3.2, NOTE 2, **quoted**:

> "This information is visible as plain text to tools that are not PDF-aware
> only if the metadata stream is both unfiltered and unencrypted."

- PDF/A-2 (2a, 2b, 2u) and PDF/A-3 allow either. Their 6.6.2.1 rules,
  tests 1–5, ask for the catalog `/Metadata` with `/Type /Metadata
  /Subtype /XML`, no `bytes` or `encoding` attribute in the packet header,
  well-formed XMP and UTF-8. No PDF/A-2 or PDF/A-3 rule tests a metadata
  stream's `Filter`.
- The only such rule is in the PDF/A-1 profile, ISO 19005-1 6.7.2 test 2:
  "The Metadata object stream dictionary in the document's catalog shall
  not contain the Filter key". Tincture writes PDF/A-2 and PDF/A-3 only
  (`set_pdf_a/2`), so it does not apply, but leaving the XMP unfiltered
  keeps a later PDF/A-1 path from needing a second change.
- The XMP is 0.38% of the stream bytes. `/EncryptMetadata false`
  (`lib/tincture/pdf/encrypt.ex`) already leaves it readable in an
  encrypted document, which agrees.

### The empty stream

An invisible signature's appearance is an empty stream; compressed, it
grows from 0 to 8 bytes. It is the only stream that grows. **Decision:** the
uniform rule holds, and it is compressed too.

## B. The rules

### Stream extent and FlateDecode

ISO 32000-1 7.3.8.2, "Stream Extent", **quoted**:

> "Every stream dictionary shall have a Length entry that indicates how many
> bytes of the PDF file are used for the stream's data. (If the stream has a
> filter, Length shall be the number of bytes of encoded data.)"

7.3.8.1, **quoted**:

> "There should be an end-of-line marker after the data and before
> endstream; this marker shall not be included in the stream length."

Table 5, `DecodeParms`, **quoted**:

> "If there is only one filter and that filter has parameters, DecodeParms
> shall be set to the filter's parameter dictionary unless all the filter's
> parameters have their default values, in which case the DecodeParms entry
> may be omitted."

Table 5, `DL`, **quoted**: "(Optional; PDF 1.5) A non-negative integer
representing the number of bytes in the decoded (defiltered) stream. … This
value shall be considered a hint only".

7.4.4.1, **quoted**: "The Flate method is based on the public-domain
zlib/deflate compression method … It is fully defined in Internet RFCs 1950,
ZLIB Compressed Data Format Specification, and 1951, DEFLATE Compressed Data
Format Specification".

What follows:

- `/Filter /FlateDecode` with no `/DecodeParms`: a content stream, a font
  program, a CMap and an ICC profile use no predictor.
- `/Length` is the compressed size.
- `:zlib.compress/1` writes the RFC 1950 (zlib-wrapped) format 7.4.4 names.
- The header stays `%PDF-1.4` (`serialize.ex:1053`); FlateDecode is PDF 1.2.
- `/DL` is PDF 1.5, and is not written.

### `/Length1` stays the decoded size

ISO 32000-1 Table 127, "Additional entries in an embedded font stream
dictionary", `Length1`, **quoted**:

> "(Required for Type 1 and TrueType fonts) The length in bytes of the
> clear-text portion of the Type 1 font program, or the entire TrueType font
> program, after it has been decoded using the filters specified by the
> stream's Filter entry, if any."

So with FlateDecode, `/Length1` is the **decoded** program size and
`/Length` the compressed size. Today both are written from one value
(`font_embed.ex:394`), which stage 2 splits.

No veraPDF profile mentions `Length1` (PDFA-2A, 2B, 2U, 3B and PDFUA-1), so
a wrong `/Length1` would pass every claim. **A rule with nothing to check
counts as passed.** Stage 2 adds its own test: in every exported `FontFile2`,
`/Length1` equals the byte size of the inflated stream.

Not 0.5.0's subject, recorded: Table 127's text after the table says of CFF
programs that "The Length1, Length2, and Length3 entries are not needed in
that case and shall not be present", and Tincture writes `/Length1` on its
`FontFile3 /Subtype /OpenType` (`font_embed.ex:397`). No committed example
embeds an OpenType font.

### Filters under PDF/A and PDF/UA

`PDFA-2B 6.1.7.2-1` (the same in 2A, 2U and 3B): "All standard stream
filters listed in ISO 32000-1:2008, 7.4, Table 6 may be used, with the
exception of LZWDecode. In addition, the Crypt filter shall not be used
unless the value of the Name key in the decode parameters dictionary is
Identity. Filters that are not listed in ISO 32000-1:2008, 7.4, Table 6
shall not be used". FlateDecode is permitted.

`PDFA-2B 6.1.7.1`:

- test 1: "The value of the Length key specified in the stream dictionary
  shall match the number of bytes in the file following the LINE FEED (0Ah)
  character after the stream keyword and preceding the EOL marker before
  the endstream keyword";
- test 2: the EOL after `stream` and before `endstream`;
- test 3: "A stream dictionary shall not contain the F, FFilter, or
  FDecodeParms keys".

`PDFA-2B 6.1.3-2`: "The keyword Encrypt shall not be used in the trailer
dictionary". An archival document is never encrypted.

PDF/UA-1: no rule in the profile mentions a filter.

### Encryption: filter, then encrypt

ISO 32000-1 7.6.2, in the text after Algorithm 1, **quoted**:

> "Stream data shall be encrypted after applying all stream encoding filters
> and shall be decrypted before applying any stream decoding filters. The
> number of bytes to be encrypted or decrypted shall be given by the Length
> entry in the stream dictionary."

Encryption runs when objects are assembled
(`serialize.ex:1124-1142`, `maybe_encrypt_object/4`), after each writer has
produced its `{:stream, head, data}`. **Compressing inside the writers
therefore gives "filter, then encrypt" with no change to `Encrypt`.** The
AES path rewrites the first `/Length ` to the ciphertext size; the pattern
needs a space after `Length`, so it does not touch `/Length1`.

0.4.1 made every stream an encrypted stream (it fixed images, soft masks,
form XObjects and widget appearances, which were not), so 0.5.0 has one
stream shape to compress.

### Signing

Nothing in `/ByteRange` handling depends on stream bytes.
`Sign.apply_signature/2` (`lib/tincture/pdf/sign.ex`) finds the reserved
`/Contents` zeros and the `/ByteRange` placeholder by the first match over
the whole file and patches fixed-width fields, so no byte moves. Both
placeholders are in the signature dictionary, which is not a stream. The
match target is a run of 16,384 or more ASCII `0` bytes, or `[0 ***…`, which
deflate output almost never contains, so compression makes an accidental
earlier match less likely, not more.

## C. Determinism

The byte locks and the committed examples depend on compression giving the
same bytes on every machine that regenerates them.

**The probe** compressed the decoded data of all 164 streams in the 14
committed examples (4,357,328 bytes) with `:zlib.compress/1` and with
`deflateInit/6` at levels 1, 6 and 9 (window 15, memLevel 8, default
strategy), took the SHA-256 of all outputs in order, and checked that every
output inflates back to its input.

**CI's own OTP builds** were measured: `setup-beam` on `ubuntu-latest`
(now Ubuntu 26.04) installs builds.hex.pm's `OTP-26.2.5.21`, `27.2.4`,
`27.3.4.19` and `28.1.1`, and all four link the system `libz.so.1`, Ubuntu
26.04's zlib 1.3.1.

| platform | zlib | `compress/1` = level 6 | level 1 | level 9 |
|---|---|---|---|---|
| Windows 11, OTP 27.3.4.x | OTP's own build | 1,674,340 `f4ac90aa…` | 1,791,693 `27ec15d7…` | 1,672,518 `4cf20a0b…` |
| Ubuntu 26.04, OTP 26.2.5.21, 27.2.4, 27.3.4.19, 28.1.1 | system 1.3.1 | same | same | same |
| Ubuntu 22.04, OTP 27.3.4.3 | system 1.2.11 | same | same | same |
| Fedora 45, its packaged OTP 27 | **zlib-ng-compat 2.3.3** | **1,701,909 `77bd76c4…`** | 1,787,087 `98e9d348…` | 1,680,544 `c18c83d7…` |

- **Classic zlib, 1.2.11 to 1.3.1, is byte-identical** on Windows, on every
  CI build and on Ubuntu 22.04. So **the byte locks stay byte locks.** That
  is already true today: the committed CIDToGIDMap streams are Flate, and CI
  regenerates them byte-identically.
- **zlib-ng is not.** It gives different bytes at every level, 1.6% larger at
  the default. On a zlib-ng system (Fedora 40 and later) `mix examples`
  would rewrite every PDF and every hash lock would fail.
- **macOS was not measured.** A Homebrew or asdf OTP on macOS links Apple's
  system libz. The measurement is two commands, given in stage 2's canary
  test.

**Decision: the settings are `:zlib.compress/1`.** Level 6, window 15,
memLevel 8, default strategy. It is what the CIDToGIDMap already uses
(`font_embed.ex:2052`), so the codebase keeps one setting. Level 9 saves
0.11% for more CPU; level 1 costs 7%.

**Decision: a zlib canary.** One named test compresses a fixed input and
asserts its bytes, so a machine with a different zlib fails one test that
says "this zlib is not the reference zlib", not every hash lock. A sentence
in `RELEASE.md` and `examples/README.md` says the same. If CI's runner image
ever moves to zlib-ng, the canary fails first; the fallback then would be to
compare documents with every stream inflated, which loses the check on the
compressed bytes themselves, and is not adopted while no CI platform needs
it.

## D. The option

- **Compression is on by default.** `compress: false` on `export/2` and
  `save/3` turns it off, for inspection and debugging.
- **`compress: false` writes exactly what 0.4.1 writes**, byte for byte:
  the CIDToGIDMap and PNG data stay Flate, as they are. That makes it a
  regression handle: every existing hash lock keeps its value under
  `compress: false`, which proves 0.5.0 changes nothing but compression, and
  a second hash pins the compressed default.
- **Plumbing.** `Tincture.export/3` (`lib/tincture.ex:2301-2316`) passes the
  option to `Serialize.export/1` (`serialize.ex:40`), which takes no options
  today. `:compress` joins `@export_options` (`lib/tincture.ex:2319`), so it
  does not trigger the unknown-option warning.
- **Types snapshot. Decision: keep `keyword()`.** `export/2` and `save/3`
  take `keyword()`, and their snapshot lines
  (`test/fixtures/public_api_types.txt:103`, `:130`) do not change. A
  named `export_option()` type would add a line and change two, for no
  caller-visible gain.
- **Telemetry.** The `[:tincture, :page]` span's `:byte_size` is the
  content stream's `/Length`, so under compression it is the compressed
  size. Its documentation (`lib/tincture/telemetry.ex:46-48`) says the
  stream is not compressed, and changes with it.
- **Open, for stage 2:** what 0.5.0 does with unknown options in the 36
  public functions other than `export/2` and `save/3` that ignore them
  today. `export/2` warns since 0.4.1 and raises in 0.5.0.

## E. The test helper

Most of the suite's byte-matching tests read content streams, appearance
streams or font programs as raw text. Under compression those bytes are
Flate, so the tests must read through a decoder first. Stage 1 builds the
decoder and moves every such test onto it, before any byte changes.

**Where:** `test/support/pdf_objects.ex`, the existing object parser, which
already reads the xref table and finds objects by structure.

- `PDFObjects.stream!(pdf, number)` returns a stream's **decoded** data.
- `PDFObjects.decoded(pdf)` returns the file with every Flate stream
  replaced by its inflated data, for `=~` matching.
- The two one-off inflaters in `field_appearance_test.exs` and
  `field_fonts_test.exs` are replaced by it.

**Its guarantees:**

1. **It locates stream data by `/Length`, never by searching for
   `endstream`.** Deflate output can contain any byte; one of the 151 Flate
   streams in the scratch build's examples ends in LF.
2. **It raises** on a stream marked FlateDecode that does not inflate or
   leaves bytes over, and on any filter it does not know, except
   `DCTDecode`, which it passes through.
3. **It decodes image data only when asked**, since PNG data carries
   predictor bytes.
4. **The complement:** for one document of every kind in section A, the raw
   export has `/Filter` on every stream except the XMP, and the list of
   unfiltered streams is exactly the XMP. That catches a writer that escapes
   compression, which presence-only tests cannot see. It cannot pass before
   compression exists, so it lands in stage 2.

**What moves.** Run against a scratch compressed build, 0.4.0's `test/`
(1,867 tests) gave 211 failures, by what reads the bytes:

| group | count | what reads the bytes | in stage |
|---|---|---|---|
| G1 | 108 | a regex, `=~` or `String.contains?` on the exported file | 1 |
| G2 | 59 | a test-local helper that slices a stream out of the file | 1 |
| G3 | 28 | `Tincture.Test.ContentStreamState.check_pdf/1`, including 14 committed example files read from disk | 1 |
| G4 | 7 | font-program extractors that read the `FontFile2`/`FontFile3` bytes | 1 |
| G5 | 9 | hash or size locks: `PDFFixtureLockTest` 6, `FormTest` 1, `SignatureTest` 1, `FormDeprecationsTest` 1 | 2 |

The suite then tests the compressed default, not `compress: false`.

**Support for the approach:** a scratch hook that undid the compression at
export time brought the same suite to 114 failures, and every one was a
limitation of the hook (encrypted ciphertext it could not inflate, moved
offsets, files read from disk, signatures altered after signing, the locks),
not a content difference. A helper that decodes inside the parsed object
model has none of those limitations.

**The widget-ownership trace** (`scripts/trace_widget_ownership.py`) finds a
stream's end by searching for `endstream` and stripping CR and LF, and hides
an inflate failure. Stage 1 changes it to read `/Length` and to inflate
Flate streams before reading.

## F. The baseline and the scratch build

### The baseline, on `1f4c344`

**The document:** A4, built with `Layout.Template` (margins 56 pt), a header
and a footer on every page in embedded LiberationSans, body text at 11 pt in
embedded LiberationSerif, 1,000 words per page from a fixed seed per page,
every page full. Built page by page, because building the whole document in
one `Template.render_document/4` call grows faster than linearly in the
input (recorded in the backlog).

**The environment:** Windows 11, OTP 27, Elixir 1.19.5, `MIX_ENV=dev`, a
fresh VM per run. CI runs OTP 28.1.1, so these are local figures.

**Memory** is measured with the build and export in one spawned worker. After
the build the worker collects its garbage, and `:erlang.memory(:total)` is
read. During `Tincture.export/1` a sampler records, every 1 ms, the maximum of
`:erlang.memory(:total)`, of the worker's process memory, and of the refc
binaries it references. **The export peak is the VM maximum minus the figure
before export:** what exporting adds to the VM. The file and every large
stream binary are off-heap refc binaries, which the process figure does not
count. Sampling at 1 ms can miss a shorter peak, so the figure is a lower
bound.

| | 100 pages | 1,000 pages |
|---|---|---|
| file size, bytes | 4,966,547 (identical in 3 runs) | 47,484,751 (identical in 3 runs) |
| export time, s | 3.83, 3.39, 1.67 | 43.76, 46.18, 47.15 |
| **export peak**, MB | 119.4, 116.6, 116.0 | 935.8, 993.4, 793.2 |
| worker heap, before export → peak, MB | 27.4 → 45.7 | 203.1 → 339.6 |
| worker refc binaries, peak, MB | 9.1–9.2 | 72.1–111.8 |

At 1,000 pages, exporting a 47.5 MB file adds 0.8–1.0 GB to the VM, about 20
bytes held per byte written, most of it outside the worker's heap. That is
the figure the streaming export needs.

## H. Order of work

**Branches.** `design-0.5.0` is the integration branch, from `main` at
`d908aa4`.

- `main` stays equal to the latest release until 0.5.0 ships. A 0.4.x fix,
  if one is needed, goes on `main`, and `main` is then merged into
  `design-0.5.0`.
- Each stage branches from `design-0.5.0` and merges back after review.
- At release, `main` is fast-forwarded to `design-0.5.0`, and
  `design-0.5.0` is deleted.

Only three kinds of commit land on `design-0.5.0`:

1. merges of `main`;
2. merges of reviewed stage branches, with `--no-ff`;
3. design-doc commits that touch only `docs/design/`, never mixed into a
   stage commit.

**Each stage ends with:**

- `mix check` green;
- CI green on its branch, on every job;
- every committed example byte-compared against `main`, with every
  difference explained;
- **the compatibility gate**: 0.4.1's `test/` tree is run against the
  stage's base and against its branch. The two failure sets must be
  identical, unless the stage intends a difference and names each one;
- **the docs search**: section G's passages, and the `@doc` of every
  function the stage touches, searched and listed, and those now false
  corrected before merge;
- a stop point for review before merge.
