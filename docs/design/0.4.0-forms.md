# 0.4.0 — forms, completed

Status, 2026-11-05: **in progress.** Stages 1, 1b, 1c, 1d, 1e, 2, 3, 4, 5a,
5b, 6a, 6b, 7, 8a-1, 8a-2 and 8b, and the subset-tag fix, are built and
merged into `design-0.4.0`. The spike is done, and releases 0.3.5 to 0.3.13
are out, each merged into `design-0.4.0` from `main`. Stage 9 remains.
Section H gives the order and what each stage ends with.

Facts about the code are given as `file:line` at the commit the passage
names. A line reference that names no commit is at `2bed2f9`, the commit the
plan was written against. Line numbers describe their commit only and do
not describe later code.

Reconciled with `v0.3.6` (`bb57903`) on 2026-10-20.

0.4.0 contains two things:

- the four behaviours deprecated in 0.3.4 become errors;
- interactive forms become usable in archival and accessible documents.

For forms, that means three changes. Every field gets a generated
appearance, so `/NeedAppearances` is never written. Fields can use embedded
fonts. And every widget is owned by a `Form` structure element.

Getting there needs two general mechanisms, which the rest of the release
builds on: form XObjects as a public primitive, and a font pipeline that
serves any content stream rather than only pages.

Three rules shape the plan:

- **Nothing breaks without a warning first.** Every change that makes working
  0.3.4 code raise is announced by a deprecation warning in 0.3.6, and raises
  only in 0.4.0. Section J lists them.
- **The bytes come before the API.** Every question whose answer depends on
  viewer or validator behaviour is settled by a spike (stage S): hand-written
  files, built without the library, checked in validators and viewers. A
  decision that depends on a spike outcome is marked **pending spike**, with
  the outcome that selects each option.
- **A validator is necessary, not sufficient.** veraPDF checks the values it
  can see. The connections between objects, and the checkpoints that need
  judgement, are verified separately, at byte level (sections F and G).

## Sources and how they are cited

- **veraPDF rules** are cited as `<profile> <clause>-<test>`, for example
  `PDFUA-1 7.18.4-1`. They are taken from the profile XML shipped in
  veraPDF 1.30.2 (`cli-1.30.2.jar`, `org/verapdf/pdfa/validation/PDFUA-1.xml`,
  `PDFA-2B.xml`, `PDFA-2U.xml`, `PDFA-2A.xml`), the same version CI runs. The
  rule texts quoted below are the profile's own `<description>` and `<test>`.
- **ISO 32000-1 clause numbers** are cited only where a veraPDF rule
  description names them, or with a passage quoted from the standard (next
  item). Any other clause number is marked **unverified**.
- **Passages of ISO 32000-1:2008 quoted verbatim**, each with its clause and
  printed page number, are cited as **quoted**. A quoted passage needs no
  veraPDF rule to name its clause. Section A cites §7.6.1 this way.
- **The OpenType specification** is cited for the OS/2 `fsType` field, from
  the OS/2 table chapter of OpenType 1.9.1, as published on Microsoft Learn.
  A passage quoted verbatim from it is cited as **quoted**, like ISO 32000-1.
- **The Matterhorn Protocol** failure conditions are cited by number, from the
  PDF Association's published table of conditions. That table does not state
  its Matterhorn version, and it was not cross-checked against the Matterhorn
  1.1 document, so the list in section F is **unverified**.
- **PAC checkpoints** are not cited anywhere. Every statement about PAC is
  **unverified**.
- **Viewer behaviour** (what Acrobat or Chromium do with a field) is
  **unverified** unless it was observed: on screen in stage S, or from saved
  bytes in the stage 5b proof, which names the library and version. Decisions
  that depended on stage S were marked **pending spike**.

A claim marked **unverified** is never the reason for a decision.

Decisions are marked in one of three ways:

- **Decision:** settled by this document.
- **Proposed — the maintainer to confirm:** the current position, which the maintainer
  confirms before the stage that implements it.
- **Pending spike:** selected by a stage S outcome, given with each option.
- **Decision (stage S, 2026-10-20):** a pending-spike decision, selected by
  the spike. Each one states its evidence and how strong it is: *observed*
  (seen in a file, a validator report or a viewer), *inferred* (concluded from
  observations that do not show it directly), or *reasoned* (argued from a
  rule's own wording, where no tool can see the case).

## A. The four deprecations become errors

### Current behaviour

The four warnings, as of 0.3.4:

| | Site | Raised when |
|---|---|---|
| W1 | `lib/tincture/pdf/ops.ex:144`, `paint_open_path/4` | `stroke/1`, `fill/1`, `fill_even_odd/1`, `clip/1`, `clip_even_odd/1` with no open path |
| W2 | `lib/tincture/pdf.ex:273`, `warn_open_marked_content/2`, from `add_page` (`pdf.ex:231`) and `set_page` (`pdf.ex:249`) | a page change while a content tag or artifact is open |
| W3 | `lib/tincture/pdf.ex:532`, `resolve_figure_bbox/2`, run by `end_structure/1` (`pdf.ex:375`) | a `:figure` that draws nothing and has no `:bbox` is closed |
| W4 | `lib/tincture/pdf.ex:600`, `warn_ignored_bbox/1`, run by `structure_options/3` (`pdf.ex:339`) | `tag/4` opens an element with an unusable `:bbox` |

All four are detected **at call time**. Each has complete information at the
moment of the call. All four already warn in 0.3.4, ending "This will raise
in 0.4.0.", so they need no 0.3.6 deprecation (section J).

### Options

1. Raise at call time, where the condition is detected.
2. Record the condition and raise from `export/2`, alongside the PDF/A and
   PDF/UA refusals (`lib/tincture.ex:1670-1720`).

### Decision: raise `ArgumentError` at call time

- **Exception.** It is `ArgumentError`, which is what every existing refusal
  raises: the export-time refusals in `check_archival/2` and
  `check_accessibility/2` (`lib/tincture.ex:1688`, `1712`), and the call-time
  ones such as `normalize_field_font/1` (`lib/tincture/pdf.ex:1311`) and the
  unknown-page check (`pdf.ex:1110`).
- **Moment.** Call time.
  - The stack trace then points at the caller's line, which is the line to
    change.
  - The export-time refusals collect findings from the whole document. These
    four conditions concern a single call.
- **No `enforce: false` escape.** `enforce:` exists so that a document can be
  iterated on while its conformance claim is not yet true
  (`lib/tincture.ex:1649-1651`). None of these four describes a document that
  is merely non-conforming. W1 and W2 produce invalid content streams. W3 and
  W4 are arguments that cannot be honoured.

### Messages

Each says what to do instead.

- **W1:** `Tincture.stroke/1 was called with no open path, so there is nothing to paint. A shape paints itself: pass its own paint argument (for example rectangle(pdf, x, y, w, h, :stroke)) instead, or start a path with move_to/3.`
  The function name and the paint example vary as today
  (`ops.ex:145-149`).
- **W2:** `Tincture.add_page/1 was called while tag(:p, ...) is open on page 1. Its marked content would begin on one page and end on another, which a content stream cannot hold. Close it before changing page.`
  `set_page/2` and the artifact wording vary as today (`pdf.ex:274-277`).
- **W3:** `Tincture.tag(:figure, ...) with alt text "…" on page 1 draws nothing, so it has no bounding box. Draw its content inside the tag, or pass bbox: {left, bottom, right, top}.`
- **W4:** `Tincture.tag/4: <problem>. Pass bbox: {left, bottom, right, top}, four numbers within the page with left < right and bottom < top, and only on :figure.`
  The `<problem>` strings are unchanged (`pdf.ex:580-587`, `571`).

A figure cannot span pages. `:figure` is a content tag, so W2 refuses the
page change while it is open. The 0.3.4 path that gave a figure closed on
another page no `/BBox` and no error (`:spans_pages`) is therefore
unreachable, and stage 1 removes it.

### Bytes

None change. Since 0.3.4, a document that triggers W1–W4 already writes no
operator, or writes the computed box (CHANGELOG 0.3.4). A document that does
not trigger them is unaffected.

### Documentation

- The `@doc` of `add_page/1` and `set_page/2` states that changing page while
  a content tag or an `artifact/2` block is open raises, because marked
  content cannot span content streams. (0.3.5 documents the warning; 0.4.0
  changes "warns" to "raises".)
- The five painting functions' `@doc` lines (`lib/tincture.ex:1054`, `1069`,
  `1084`, `1099`, `1114`) change from "0.4.0 will raise rather than warn" to
  "raises".
- `tag/4`'s `:bbox` and figure paragraphs (`lib/tincture.ex:1427`, `1447`)
  change the same way.

CHANGELOG, under `### Breaking`:

- **`stroke/1`, `fill/1`, `fill_even_odd/1`, `clip/1` and `clip_even_odd/1`
  raise with no open path.** *Migration:* pass the shape's own paint argument,
  `rectangle(pdf, x, y, w, h, :fill)` in place of
  `rectangle(pdf, x, y, w, h) |> fill()`, or open a path with `move_to/3`.
- **`add_page/1` and `set_page/2` raise while a content tag or an `artifact/2`
  block is open.** *Migration:* close the tag before changing page, and open
  a new one on the next page.
- **A `:figure` that draws nothing raises when it closes.** *Migration:* draw
  the figure's content inside the tag, or pass `bbox:`.
- **An unusable `:bbox` raises.** *Migration:* pass four numbers within the
  page, ordered, and only on `:figure`; or omit it and let the box be
  computed.

Every one of these warned in 0.3.4, so a caller with no warnings in 0.3.4 is
unaffected.

### Signing an encrypted document (stage 1b)

**Finding.** Signing an encrypted document has never worked. In every
release that has both features, v0.2.0 to v0.3.7, `export/2` raises
`ArgumentError` with "could not find the reserved signature space in the
serialised document", and no file is produced. The encryptor encrypts the
signature dictionary's placeholder `/Contents` (the hex-string branch of
`scan_strings/3` in `lib/tincture/pdf/encrypt.ex`) before
`Tincture.PDF.Sign.apply_signature/2` looks for it (`export/1` in
`lib/tincture/pdf/serialize.ex`). Nothing in the code was written for the
combination, and nothing refuses it, so the message names an internal
symptom rather than the unsupported combination. The same document signed
without encryption exports, and verifies with openssl and pyHanko
(*observed*).

**Decision: refuse at call time.** `sign/3` on an encrypted document, and
`encrypt/2` on a signed one, raise `ArgumentError` at once:

> Tincture.sign/3 was called on a document that is encrypted. Tincture cannot sign an encrypted document: sign it without encryption, or encrypt it without a signature.

`encrypt/2` uses the mirror wording, naming the function and arity called.
There is no deprecation: the combination never produced a file in any
release, so no code that works today stops working (section J).

**What the standard says.** ISO 32000-1 §7.6.1, page 55, quoted from the
standard's text rather than named by a veraPDF rule:

> Encryption applies to all strings and streams in the document's PDF file,
> with the following exceptions:
> • The values for the ID entry in the trailer
> • Any strings in an Encrypt dictionary
> • Any strings that are inside streams such as content streams and
> compressed object streams, which themselves are encrypted

The signature dictionary's `/Contents` is not among the exceptions, and no
other passage of ISO 32000-1 treats signatures and file encryption together.
Read literally, the signature value of an encrypted document is encrypted
like any other string. In practice, pyHanko 0.38.0, signing an encrypted
document, encrypts every other string it writes and leaves `/Contents` in the
clear, and validates its own result (*observed*). ISO 32000-2 (PDF 2.0) was
not checked.

**Supporting the combination is out of scope** (section I).

### Path state: W5, W6 and W7 (0.3.8 and 0.3.9, then stage 1c)

**Decision, 2026-10-21.** Two released defects concern how Tincture ends a
path: `paint: :none` wrote `n`, which ends the path its documentation says a
later `fill/1` or `clip/1` paints; and an image or gradient drawn while a path
is open was written inside the path object. A survey of every operation
Tincture can write between a path and its paint found the problem wider: none
but path construction is allowed there.

**What the standard says (quoted).** ISO 32000-1:2008:

- Figure 9, "Graphics Objects", page 113: the path object's "Allowed
  operators: • Path construction"; it is entered by "m, re" and left by
  "Path-painting operators", or by "W, W\*" to the clipping path object,
  whose "Allowed operators" are "None".
- The EXAMPLE under Figure 9, page 113: "Inside the path object, additional
  path construction operators are permitted, as are the clipping path
  operators W and W\*, but not general graphics state operators such as w or
  J. A path-painting operator, such as S or f, ends the path object and
  returns to the page description level."
- §8.5.3.1, Table 60, page 135, on `n`: "End the path object without filling
  or stroking it."
- §8.2, page 114: "there is no semantic significance to the exact arrangement
  of graphics state operators. A conforming reader or writer of a PDF content
  stream may change an arrangement of graphics state operators to any other
  arrangement that achieves the same values of the relevant graphics state
  parameters for each graphics object."

**The rule.** Between a path's first construction operator and its paint,
Tincture writes only path construction, then optionally `W` or `W*`, then the
paint. A call made while a path is open falls into one of four classes:

1. **Path construction** (`move_to/3`, `line_to/3`, `bezier/7`, a shape with
   `paint: :none`) extends the path.
2. **Paint or clip** (`stroke/1`, `fill/1`, `fill_even_odd/1`, `clip/1`,
   `clip_even_odd/1`, a shape with a paint) ends it and paints all of it. A
   shape's `re` joins the open path, so a shape drawn with a paint while a
   path is open paints that path too, as PDF defines it; `rectangle/6`,
   `line/6` and `circle/5` say so in their `@doc`.
3. **State setters** (`set_fill_color/2`, `set_stroke_color/2`,
   `set_line_width/2`, `set_line_cap/2`, `set_line_join/2`, `set_dash/3`,
   `set_miter_limit/2`, `set_alpha/1,2`) are written by the serialiser just
   before the path's first construction operator, as page 114 permits. The
   recorded operations keep call order; only the written order changes. No
   warning, in any version.
4. **Drawing or structure** (every text function, `image_jpeg/6`,
   `image_png/6`, `linear_gradient/6,7`, `radial_gradient/6,7`,
   `save_state/1`, `restore_state/1`, a content `tag/3,4`, `artifact/2`)
   warns in 0.3.8 (W5) and raises in 0.4.0. `place_form_xobject/4,5` already
   raises (section B).

**`paint: :none`** writes the shape's construction operators only and leaves
the path open. A following paint paints it and a following clip clips it. If
a class-4 operation or the end of the stream comes first, the serialiser ends
the path with `n` there, which is the bytes `:none` always wrote in that case.
From 0.4.0 the serialiser does this for any open path, not only one a `:none`
shape left; see "The serialiser never writes a path left open" below.

**A path left open** when the page is left (`add_page/1`, `set_page/2` to
another page) or the document exported is ended with `n` in 0.3.8 and warns
(W6); 0.4.0 raises. This includes a `:none` shape nothing painted. There is no
`enforce: false` escape: like W1–W4 it is invalid content, not a conformance
claim.

**W5, 0.3.8.**

- **Condition and moment:** at the call to a class-4 function, before its
  operation is appended, when the current page's path is open (W1's
  `path_open?/1`).
- **Warning:**
  `Tincture.text_at/4 was called while a path is open, so the text would be written inside the path, where PDF does not allow it. A path holds only path construction until stroke/1, fill/1 or clip/1 paints it, or a shape's own paint argument does: paint the path first, or draw this before starting it. This will raise in 0.4.0.`
  "the text" becomes "the image", "the gradient", "the saved graphics
  state", "the restored graphics state" or "the marked content". The function
  and arity are those called where an explicit clause tells them apart, the
  highest arity otherwise.
- **Bytes:** as before, except that a path made by `:none` is ended with `n`
  before the operation.

**W6, 0.3.8.**

- **Condition and moment:** at `add_page/1`, at `set_page/2` to another page,
  and at `export`, when the page being left, or the current page at export,
  has a path open.
- **Warning:**
  `Tincture.add_page/1 was called while a path is open on page 1 that nothing has painted. A path draws nothing until stroke/1, fill/1 or clip/1 paints it, so it is ended unpainted. Paint it, or remove it. This will raise in 0.4.0.`
  The same for `set_page/2` and export, naming the function called.
- **Bytes:** `n` at the end of the path.

**W7, 0.3.9.** *Decision, 2026-10-22.* W5 checks a tag or artifact only when
it opens. A path started inside its callback and painted after it is not
caught: 0.3.8 writes `BDC m l EMC S`, with the `EMC` inside the path, and does
not warn. Stage 1c's serialiser ends any open path with `n` before a
non-path operator, which would make the same calls write `BDC m l n EMC S`:
the `S` would paint nothing, and the line would disappear without an error.
0.3.8 never warned about the pattern, so it gets its own deprecation in a
separate release.

- **Condition and moment:** when a content tag or an `artifact/2` block
  closes, that is, when its `EMC` would be written, while a path is open in
  the current stream that was not open when that tag or artifact opened. A
  path already open when it opened is W5's case, at the open. W7 fires once
  per path, at the first such close: an enclosing tag that closes later does
  not fire again for the same path. A grouping element writes no `BDC` or
  `EMC` and never fires it.
- **Warning, for a tag:**
  `Tincture.tag/4 closed tag(:p, ...) with a path still open, so its end would be written inside the path, where PDF does not allow it. Paint the path with stroke/1, fill/1 or clip/1 before the tag closes. This will raise in 0.4.0.`
  The tag's name is the one given, as in W2.
- **Warning, for an artifact:**
  `Tincture.artifact/2 closed with a path still open, so its end would be written inside the path, where PDF does not allow it. Paint the path with stroke/1, fill/1 or clip/1 before the artifact closes. This will raise in 0.4.0.`
- **Bytes:** unchanged from 0.3.8: `BDC m l EMC S`.

**0.4.0 (stage 1c).** W5, W6 and W7 raise `ArgumentError` at the same
moments. W5 and W7 keep their messages without "This will raise in 0.4.0.".
W6 also loses "so it is ended unpainted", since a refused call ends nothing:

`Tincture.add_page/1 was called while a path is open on page 1 that nothing has painted. A path draws nothing until stroke/1, fill/1 or clip/1 paints it. Paint it, or remove it.`

CHANGELOG, under `### Breaking`:

- **Drawing text, an image or a gradient, saving or restoring graphics state,
  or opening a tag or artifact, while a path is open raises.** *Migration:*
  paint the path first, or draw the content before starting it.
- **Leaving a path unpainted raises** at a page change or at export.
  *Migration:* paint it, or remove it.
- **Closing a tag or artifact over a path started inside it raises.**
  *Migration:* paint the path before the tag or artifact closes.

W5 and W6 warned in 0.3.8 and W7 in 0.3.9, so a caller with no warnings in
0.3.9 is unaffected.

**The serialiser never writes a path left open (0.4.0, stage 1c).**
*Decision, 2026-10-22.* In 0.3.8 and 0.3.9 the serialiser ends an open path
with `n` before a class-4 operator only when the path's last construction was
a `:none` shape; any other open path keeps the operator inside it. At the end
of a stream it ends any open path. From 0.4.0 it ends any open path with `n`
before every operator that is not path construction, painting, clipping or a
class-3 setter: text, an image, a shading, `q`, `Q`, `BDC`, `BMC`, `EMC` and
an XObject placement. It also ends one at the end of the stream, with the
path's setters written before it. After a `:none` shape the `n` follows the
construction and the setters come after it, as `:none` always wrote.

With W5, W6 and W7 raising, no public call reaches this: every route is
refused first. It is reached only through `Tincture.PDF.append_current_op/2`,
which is published for internal use, and stays as the output guarantee for
that route: no content stream ends inside a path object or holds a non-path
operator inside one. A test builds such streams through
`append_current_op/2` and serialises them directly.

## B. Form XObjects as a public primitive

### Current behaviour

Line numbers are at `290283e`, after stages 2 and 3.

- **One private writer.** `form_xobject/4` (`lib/tincture/pdf/serialize.ex:1412-1419`)
  takes width, height, a content string and a resource string. It writes
  `/BBox [0 0 w h]` and no `/Matrix`.
- **Three callers.** It is used only by the checkbox, radio and push-button
  appearance builders (`serialize.ex:1314-1390`). Each assembles its content
  as a string, not from drawing operations.
- **Resources as strings.** The only font it carries is the push-button
  caption's inline `/Helv` Type1 dictionary (`serialize.ex:1404-1406`).
- **No `/XObject` resources but images.** Page XObject resources list images
  only (`xobject_resources/2`, `serialize.ex:999`).
- **Operations live in page streams.** Every drawing function appends to the
  stream `{:page, pdf.current_page}`, held in `pdf.pages`, through
  `append_current_op/2` and the one writer `append_to_stream/3`
  (`lib/tincture/pdf.ex:255`). They are read back with
  `PDF.stream_operations/2` (`pdf.ex:239`).

### Options for the API

1. **A builder over a separate document value.** It is drawn into and then
   attached. This is rejected: fonts, images and alpha states are registered
   on the document, so they would have to be merged back afterwards.
2. **Redirect the existing drawing functions inside a callback**, the way
   `tag/4` scopes structure. The callback receives the document, and every
   drawing call inside it appends to the XObject's operations instead of the
   page's.
3. **Explicit operation lists** passed to a constructor. This is rejected: it
   would make the drawing API a second time, as data.

### Decision: option 2

The new public API:

```elixir
pdf
|> Tincture.form_xobject(:stamp, 200, 40, fn pdf ->
  pdf
  |> Tincture.set_font("Body", 10)
  |> Tincture.text_at(4, 14, "APPROVED")
  |> Tincture.rectangle(0.5, 0.5, 199, 39, :stroke)
end)
|> Tincture.place_form_xobject(:stamp, 72, 600)
|> Tincture.place_form_xobject(:stamp, 72, 300, scale: 0.5)
```

`form_xobject(pdf, name, width, height, fun)`:

- **The name** is an atom or a non-empty string, normalised to a string, so
  `:stamp` and `"stamp"` are one name. It must be unique: a second definition
  raises `ArgumentError`.
- **The coordinate space** is `[0 0 width height]`, with its origin at the
  bottom left, as on a page.
- **The callback** is run with the document's drawing target set to the
  XObject. Inside it, every drawing, text, colour, state and image function
  works unchanged.

**Decision (stage 4 plan, 2026-10-21): drawing state around the callback.**

- **Facts.** The only drawing state the document struct holds is
  `current_font`, and setting it writes no operator: each text operation
  carries its font and is written as its own `BT … Tf … ET`. Colours, line
  width, dash, alpha and the clip exist only as operators in the stream.
  Nothing in Tincture omits an operator because tracked state says it is
  already set.
- **The callback starts from a fixed state.** The XObject's operations start
  empty, and `current_font` starts at `{"Helvetica", 12}`, whatever the page
  had set. The XObject's bytes therefore do not depend on what the page did
  before the call.
- **On return, the caller's state is restored**: the drawing target, the
  `current_font` at the call, and the `operations` mirror. Drawing after the
  call produces exactly the page bytes it would have produced without it.
- **At placement, the XObject inherits.** ISO 32000-1 §8.10.1, page 218,
  **quoted**: `Do` saves the graphics state, concatenates `/Matrix`, clips to
  `/BBox`, paints and restores, and "Except as described above, the initial
  graphics state for the form shall be inherited from the graphics state that
  is in effect at the time Do is invoked." So an XObject never changes the
  page's state, and it inherits the CTM, the clip and every parameter it does
  not set itself, such as the fill colour. That is the definition of a form
  XObject, and the `@doc` says so plainly. There is no reset prologue.
- **Refused at the callback's end:** an unbalanced `save_state/1` and
  `restore_state/1`, since q and Q "shall be balanced within a given content
  stream" (ISO 32000-1 §8.4.2, page 124, **quoted**); and a path left open,
  which would never be painted.

**Decision (stage 4 plan, 2026-10-21): what the callback refuses.** Only
what the XObject's content needs is allowed: drawing, state, text, images and
fonts. Everything else raises `ArgumentError`, naming the function and arity
called. Allowing a refused call later is additive; refusing an allowed one
would be breaking.

- **Allowed:** every drawing, path, colour, state, text and image function;
  `set_font/3`; registering a TrueType or OpenType font; the read-only
  `tagged?/1`, `pdf_a_violations/1` and `pdf_ua_violations/1`.
- **Refused:**
  - `add_page/1` and `set_page/2`;
  - `tag/3,4` and `artifact/2`, which is the reuse guarantee below;
  - `link/6,7` and `text_link/5,6`;
  - every form-field function, and `sign/3`;
  - `add_bookmark/3`;
  - document settings: `set_metadata/2`, `set_language/2`, `set_pdf_a/2`,
    `encrypt/1,2` and `page_size/2`;
  - `export/1,2` and `save/2,3`;
  - a nested `form_xobject/5`, and `place_form_xobject/4,5`.

  Annotations, bookmarks and structure elements belong to pages and to the
  document, not to content streams. A placement inside a definition would
  need `/Fm` resources inside XObjects, an allocation order with the inner
  XObject first, and recursion in figure bounds; nothing in 0.4.0 needs it.
- **Where the guards are.** Each guard sits in the `Tincture.PDF` function
  the public call reaches, so the layout modules are covered too. In a tagged
  document, `Layout.Box` and `Layout.Table` tag themselves, so they raise
  inside the callback; `Layout.Template` adds pages, so it raises in any
  document.

`place_form_xobject(pdf, name, x, y, opts)`, with `place_form_xobject/4`
as an explicit clause:

- Draws the XObject on the current page, with its origin at `(x, y)`, as
  `q sx 0 0 sy x y cm /FmN Do Q`.
- **Options (decision, stage 4 plan):**

  | Given | Scale |
  |---|---|
  | nothing | `sx = sy = 1` |
  | `scale: s` | `sx = sy = s` |
  | `width: w` only | `sx = sy = w / bbox_width`, uniform |
  | `height: h` only | `sx = sy = h / bbox_height`, uniform |
  | `width:` and `height:` | `sx = w / bbox_width`, `sy = h / bbox_height`: stretched, as images are |
  | `:scale` with `:width` or `:height` | refused |

  A scale equal to an integer is written as that integer. Rotation is out of
  scope (section I).
- **Refused:** an unknown name, including one defined later; a non-positive
  or non-numeric `:scale`, `:width` or `:height`; an unknown option; and a
  placement while a path is open in the current stream. A placement draws
  with its own `q … Q`, which cannot appear inside a path object.
- **In a tagged document** the placement is content, like any other drawing
  operation, and behaves as an image does. For PDF/UA it must sit inside a
  content tag or an `artifact/2` block; that is checked by veraPDF
  (`PDFUA-1 7.1-3`), not by Tincture. Inside a tag, the `Do` falls within
  that tag's marked content.
- **In a `:figure`**, the figure's computed `/BBox` includes the XObject's
  `/BBox` transformed by the placement matrix. `FigureBounds.compute/4`
  takes a lookup from name to XObject size for that.

### Reuse across structure elements

**Decision (stage S, 2026-10-20), as amended after review.** **Reuse is
always allowed: a form XObject cannot contain marked content.**

- **The guarantee.** The callback of `form_xobject/5` refuses `tag/4` and
  `artifact/2` with `ArgumentError` (this section, "Refused inside the
  callback", `docs/design/0.4.0-forms.md:239-241` at `034a12a`). So an
  XObject's content carries no MCIDs of its own.
- **So reuse is safe.** Such an XObject takes its structure from the
  marked-content sequence around each `Do`, like an image placed twice. It
  may be placed any number of times, inside any structure elements, and
  `place_form_xobject/5` refuses nothing on that account.
- **Why that is the condition.** The case `PDFUA-1 7.20-2` forbids is an
  XObject that carries MCIDs and is referenced more than once. In the
  veraPDF 1.30.2 profile, its description reads "The content of Form XObjects
  shall be incorporated into structure elements according to
  ISO 32000-1:2008, 14.7.2", its test is `isUniqueSemanticParent == true`,
  and its error message is "Form XObject contains MCIDs and is referenced
  more than once". The guarantee keeps that case from arising.
- **Evidence: reasoned**, from the rule's own wording. veraPDF and PAC both
  pass one XObject placed inside two different `P` elements and inside one
  `P` alike, and neither tells the two cases apart. 7.20-2 is evaluated once
  per `Do`, and can fail only for an XObject with MCIDs of its own. That is a
  validator blind spot, so neither tool's pass is the evidence.
- **The guarantee is tested** (tests, below). If it is ever relaxed, that
  test fails, and this reuse rule must be revisited before the change lands.

The new API is new in 0.4.0, so this is backward compatible.

### Internal model

- **Content streams instead of pages.** The document's operations are
  addressed as content streams, keyed `{:page, n}`, `{:xobject, name}` or
  `{:appearance, …}`.
- **The document struct does not change in stage 2.** `Tincture.PDF.t` is a
  public struct type, and the types-and-specs snapshot pins it, so stage 2
  changes none of its fields:
  - the `pages` field keeps its name and type, and page streams stay in it;
  - a stream of another kind that the caller draws gets its own field, added
    by the stage that introduces it (stage 4 for `{:xobject, _}`). That is an
    additive type change, recorded in the snapshot, with its reason, in that
    stage.
  - **Decision (stage 5b plan, 2026-10-23): `{:appearance, …}` streams have
    no struct field.** They are a pure function of `form_fields` and the
    fonts' metrics. They are generated inside the serialiser, and passed to
    font embedding as the `:extra_streams` that stage 5a's synthetic lists
    already use. A field holding them would be a second source of truth for
    each form field.
- **One accessor.** `PDF.page_operations/2` becomes a special case of
  `PDF.stream_operations(pdf, key)`. In stage 2, `stream_operations/2` is
  `@doc false`. **Decision (stage 4 plan): it stays `@doc false` in stage 4.**
  Publishing it would commit to the key format, including the appearance
  keys of stage 5b, whose shape is not settled; publishing it later is
  additive.
- **One write path.** `append_current_op` appends to the stream named by
  `current_stream`. In stage 2, `current_stream` is a function returning
  `{:page, pdf.current_page}`, not a field: a field would duplicate
  `current_page` and give two sources of truth, and until a form XObject
  callback exists nothing can make the two differ.
- **Decision (stage 4 plan): the stage-4 fields.** Two fields are added:
  - `current_stream: {:xobject, xobject_name()} | nil`, an **override**,
    `nil` outside a callback. `current_stream/1` returns it when set, and
    `{:page, pdf.current_page}` otherwise, so outside a callback there is
    still one source of truth;
  - `form_xobjects: %{optional(xobject_name()) => form_xobject()}`, keyed by
    the normalised name, where `form_xobject()` is
    `%{id: pos_integer(), width: number(), height: number(), operations: [op()]}`
    and `id` is the definition order.

  The single writer `append_to_stream/3` gains an `{:xobject, name}` clause,
  so it stays the one function that writes any stream.
- **A placement is an operation:** `{:form_xobject, name, x, y, sx, sy}`.
  The public `op()` union widens by `form_xobject_op()`, recorded in the
  snapshot with that reason.
- **The `operations` field is a public mirror of the current stream's
  operations.** It is kept for compatibility: removing a public struct field
  is breaking, and no deprecation warning can be attached to reading one.
  Nothing in `lib/` reads it. Its writers are `append_to_stream/3` and one
  private `sync_operations_mirror/1`, which `set_page/2` and the
  `form_xobject/5` callback's entry and return use. Inside the callback it
  holds the XObject's operations; after return, the page's again.
- **Appearance streams are content streams too**, keyed
  `{:appearance, field_name, widget_index, state}`. They are generated at
  serialisation time from field data (section D), and they go through the
  same font discovery (section C) and the same content-stream writer as
  everything else.
  - For a text or choice field, `widget_index` is 0 and `state` is `:n`, the
    normal appearance, the only one written.
  - Their font is named by the `/DA` alias, not by `font_resources/2`
    (section C, "Standard-14 fonts on fields").
  - `stream_keys/1` does not list them: it lists the struct's streams.

### `/BBox`, `/Matrix` and resources

- **`/BBox`** is `[0 0 width height]`, given by the caller.
- **`/Matrix`** is omitted. ISO 32000-1 §8.10.2, Table 95, page 218,
  **quoted**: "Default value: the identity matrix [ 1 0 0 1 0 0 ]."
  Placement is expressed in the page's content stream instead:
  `q a 0 0 d x y cm /FmN Do Q`. That keeps the XObject reusable at
  different positions and scales, with one object.
- **Resources** are collected per stream, by the same functions that collect
  them for pages:
  - `font_resources/2` (`serialize.ex:971`);
  - `xobject_resources/2` (`:999`);
  - `ext_gstate_resources/1`;
  - `shading_resources/1`.

  They take a stream's operations since stage 2. Resource names are local to
  each stream, as `/F1…` already are per page. `/Resources` is always written
  in a public XObject, even when empty: Table 95 calls it "Optional but
  strongly recommended".
- **The page's own `/XObject` resources** gain `/FmN` entries after the
  images' `/ImN` entries. `N` is the XObject's definition id, as `/ImN`
  carries the image id.
- **Each form XObject is one indirect object**, however many times it is
  placed. **Decision (stage 4 plan):** every defined XObject is written,
  placed or not, as every registered image is.
- **Allocation (decision, stage 4 plan):** form XObjects are allocated
  immediately after images, in definition order. With none, every later
  object id is unchanged, so a document without XObjects does not change by
  one byte.
- **`stream_keys/1`** lists the page streams in page order, then the XObject
  streams in definition order, so font discovery (stage 3) sees XObject
  text.
- **No telemetry span** is emitted for an XObject stream; one can be added
  later.

### How `form_xobject/4` is replaced

- **Stage 4: one writer, two callers.** Public form XObjects are written by
  the existing `form_xobject/4`, unchanged, so it is already the one writer
  for every form XObject. Their content and resources are produced from
  operations by the shared stream serialiser (the same resource collectors
  and content-stream writer a page uses) and passed to it as strings. The
  three button builders still pass strings they assemble themselves, so
  `form.pdf` does not change.
- **Stage 6a:** the button builders move onto operation lists too, and
  `form_xobject/4`'s signature changes from
  `(width, height, content_string, resource_string)` to
  `form_xobject(bbox, {content, resources})`. The content and resources come
  from one of two producers, both serialising operations through the shared
  content-stream writer:
  - **`xobject_stream`** for public form XObjects, with the page's resource
    collectors, so fonts are named as on a page;
  - **`widget_stream`** for every widget appearance (text, choice, checkbox,
    radio, push button, signature), whose fonts are named by the field's
    `/DA` alias and reference the document's one object for the font
    (section D, "`/DA` and `/DR`").

  A single `(bbox, stream_key)` signature, with the content and resources
  from the stream serialiser for every caller, does not fit widget
  appearances: their resources are `/DR`'s objects, which the page's
  collectors do not produce. Stage 6a changes no output byte; it is proved
  by byte identity.
- The three button builders stop assembling strings. They produce operation
  lists into appearance streams (section D).

### What it must not preclude

Patterns (ROADMAP item 5) need a tiling pattern's cell. Soft masks on drawn
content (ROADMAP item 6) need a transparency group form XObject as the
mask's `/G`. Both are content streams with their own resources, which is
exactly what `{:xobject, name}` streams are. Two things are kept open:

- the stream key space is open, so a later `{:pattern, name}` or `{:group, name}`
  is an addition rather than a change;
- `form_xobject/4` writes the dictionary from a map of entries, so `/Group`
  (needed for soft masks; ISO 32000-1 11.6.5, **unverified**) can be added
  without restructuring.

Neither patterns nor soft masks are built in 0.4.0.

## C. The font pipeline beyond pages

### Current behaviour

Font handling is coupled to pages in three places:

1. **Discovery.** `FontEmbed.build_embedded_font_objects/3`
   (`lib/tincture/pdf/font_embed.ex:32-48`) walks `page_numbers` and
   `PDF.page_operations/2`. `font_names_from_operations/1` (`:107-115`)
   recognises only `{:text_at, …}` and `{:text_at_rotated, …}`.
2. **Subsetting.** `used_char_codes_by_font/2` (`:117` ff.) and the other
   `*_by_font` collectors (`:33-38`) walk the same page operations.
3. **Resource naming.** `font_resources/2` (`lib/tincture/pdf/serialize.ex:945-967`)
   names `/F1…/Fn` per page.

More facts bound the design:

- **Fields refuse embedded fonts.** `normalize_field_font/1`
  (`lib/tincture/pdf.ex:1307-1316`) raises for anything but the standard 14.
- **`/DR` is standard 14 only.** `acro_form_font_resources/1`
  (`serialize.ex:769-777`) writes inline standard-14 Type1 dictionaries with
  `/Encoding /WinAnsiEncoding`.
- **An embedded font is simple only for ASCII text.** A TrueType or OpenType
  font becomes a `Type0` font as soon as any text drawn with it is outside
  7-bit ASCII (`use_type0_embedded_font?/2`, `font_embed.ex:2847-2849`;
  `Object.unicode_text?/1`, `font_embed.ex:170`). Otherwise it is a simple
  `/TrueType` font with `/WinAnsiEncoding` (`embedded_font_object/3`,
  `font_embed.ex:2434-2440`). No path writes a simple font carrying codes
  128–255.
- **Standard-14 text is not WinAnsi-encoded.** Text drawn with a standard-14
  font is encoded by `Object.format_text/2` in `:pdf_text` mode
  (`serialize.ex:1721-1722`), which writes anything outside 7-bit ASCII as
  UTF-16BE with a byte order mark (`lib/tincture/pdf/object.ex:58-68`). The
  font dictionary carries no `/Encoding` on pages, and `/WinAnsiEncoding` in
  `/DR` and on the push-button caption. Measured at `2bed2f9`: `text_at`
  with `"Größe"` in Helvetica writes `<FEFF0047007200F600DF0065> Tj`. The
  appearance generator in this design must not reuse that path for
  standard-14 text (section D). The page-text behaviour is a defect outside
  the scope of this document.
- **No WinAnsi table existed in `lib/` at `2bed2f9`.** Nothing mapped a
  character to its WinAnsi code or decided whether a string is
  WinAnsi-encodable. 0.3.6 added one, `Tincture.PDF.WinAnsi`
  (`lib/tincture/pdf/win_ansi.ex`), for the J4 warning; stage 5a reuses it.
- **The whole-font embed exists already.** `register_ttf_font/4` and
  `register_otf_font/4` accept `subset: :none`, which embeds the font
  verbatim (`lib/tincture.ex:644-650`).
- **Every registered embedded font has cmap data (stage 1e).** Through
  stage 1d, a font whose `cmap` gave no mapping was registered, and so was an
  `OTTO` file whose tables did not parse. Three paths served such a font:
  the fallback chain judged its coverage from the OS/2 Unicode and code page
  ranges (`lib/tincture.ex:2958-2979` at `a6a0906`); a `Type0` font got
  `/CIDToGIDMap /Identity`, so glyph = code point
  (`lib/tincture/pdf/font_embed.ex:1926-1929`, by way of `:1941`); and the
  subsetter skipped it and embedded it whole (`font_embed.ex:414`, `:478`).
  Stage 1e refuses such a font at registration (section J) and removes those
  paths. So W9, the field font checks and an editable field's whole-cmap
  coverage (below) always have a cmap to read.

### Decision: discovery and subsetting over every content stream

- **The input changes.** Font embedding takes the list of content streams to
  be written, instead of `page_numbers`: pages, `{:xobject, _}` and
  `{:appearance, …}`. Every `*_by_font` collector walks the same list.
- **Published functions keep their contracts.** A function in `@public_api`
  or `@internal_published` whose arguments name pages, such as
  `FontEmbed.build_embedded_font_objects/3`, keeps accepting what it accepts
  today, and translates page numbers into `{:page, n}` keys. The stream-list
  version is a new internal function alongside it.
- **One subset per font for the whole document**, as today: one font object,
  one `FontFile2`/`FontFile3`, referenced from every stream that uses it.
- **Appearance streams are built first.** They are generated as operation
  lists before font embedding runs. The serialiser's order becomes:
  1. build appearance operation lists;
  2. collect the streams;
  3. embed fonts;
  4. allocate objects;
  5. write.
- **`font_resources/2` takes a stream's operations**, not a page's. Its
  output format does not change.

### Acceptance

1. **A glyph used only in an appearance stream is in the subset.** The test is
   a document whose page text never uses `Q`, with a read-only text field
   whose value is `"Q"`. The font's subset must contain the glyph, checked by
   parsing the embedded `glyf`/`loca` (or `CFF `) and the font's `/Widths`.
   - The veraPDF evidence is `PDFA-2B 6.2.11.4.1-2` ("Embedded fonts shall
     define all glyphs referenced for rendering within the conforming file").
   - It runs on the archival form example (section G).
2. **Output with pages only stays byte-identical.** Every committed example in
   `examples/output/`, other than `form.pdf`, is byte-compared against `main`
   at the end of each stage that touches the pipeline. `form.pdf` changes by
   design (section D).
3. **The `*_by_font` collectors** are tested against a synthetic stream list
   that mixes pages and an XObject.
4. **One font dictionary and one font program for a shared font.** A
   document whose page text and editable field use the same font, embedded
   whole, has exactly one `Type0` font dictionary and one `FontFile2` object
   for it. The page's `/Font` resource and `/DR` name the same dictionary.

### Decision: fields may use embedded fonts

`normalize_field_font/1` accepts any font registered with
`register_ttf_font/4` or `register_otf_font/4`, as well as the standard 14,
under the conditions below, **for text and choice fields**. This is new API:
today the same call raises (`pdf.ex:1713-1725` at `416a9db`).

**Decision (stage 5a plan, 2026-10-21): push buttons, checkboxes, radio
buttons and signature fields keep the standard 14 in stage 5a.** A push
button's caption is measured with standard-font metrics and drawn with an
inline `Type1` dictionary whose `/BaseFont` is the field's font
(`push_button_caption/3`), so an embedded name there would write a `Type1`
font that does not exist. Checkboxes and radio buttons draw no text.
Embedded fonts on push-button captions arrive in stage 6b, with appearances
built from operations. Until then such a field given an embedded font raises,
as it does today, and the message still names the standard 14.

### Which fields are editable

A viewer draws characters the document did not contain only where a person
can type: a text field that is not `read_only:`, and a choice field with
`editable: true` that is not `read_only:`. Those are the **editable fields**
of this section.

Every other field's possible values are known when the document is written:

- a read-only field shows its value;
- a non-editable choice field shows one of its `:options`.

So those fields are subset like any other text, and the subset includes every
option's glyphs, not only the selected one's.

### Decision: full embed only on request

**The problem.** A viewer that lets someone edit a field regenerates its
appearance from `/DA` and the font in `/DR`, with whatever characters were
typed. It can only draw glyphs the embedded font program contains. A subset
holds only the glyphs Tincture saw.

**Options.**

1. **Embed the whole font automatically** for any font used by an editable
   field. The cost is size, often hundreds of kB, and it is silent.
2. **Subset, plus a documented limitation**: an edited value can only use
   glyphs that were in the subset. The form fails in the hands of the person
   filling it, not the author.
3. **Refuse** an embedded font on an editable field unless the caller asks
   for the whole font.

**Decision: option 3**, confirmed 2026-10-20.

- `text_field/7` and `choice_field/7` gain `full_font: true`. With it, the
  field's font is embedded without subsetting, for the whole document. It is
  still one font object.
- An embedded font on an editable field must be embedded whole. That is given
  by either `full_font: true` on the field, or registering the font with
  `subset: :none`. Without either, the field call raises `ArgumentError`:

  ```
  text field "full_name" uses the embedded font "Body", which is subset to the
  glyphs this document draws. A viewer cannot render characters someone types
  into the field if they are missing from the subset. Pass full_font: true, or
  register the font with subset: :none, to embed the whole font; or make the
  field read_only: true.
  ```

- `full_font: true` is accepted on text and choice fields, and ignored with a
  standard-14 font, which is never embedded.
- **`subset: :none` counts.** A font registered with `subset: :none` is
  already embedded whole, so it needs no extra flag on the field.
- **Why not option 1.** The size cost lands without the caller choosing it.
- **Why not option 2.** It ships a form whose ordinary use produces broken
  output.

### Embedding permission for editable-field fonts

**The OpenType rule.** The OS/2 `fsType` field (OpenType 1.9.1, OS/2 table)
carries a usage permission in bits 0–3, with values 0, 2, 4 or 8:

- **0, Installable:** the font may be embedded and permanently installed.
- **2, Restricted License:** the font "must not be modified, embedded or
  exchanged in any manner without first obtaining explicit permission".
- **4, Preview & Print:** the font may be embedded for viewing or printing;
  "Documents containing Preview & Print fonts must be opened 'read-only'; no
  edits may be applied to the document."
- **8, Editable:** as Preview & Print, and "editing is permitted, including
  ability to format new text using the embedded font, and changes may be
  saved."

Bit 8 (`0x0100`) forbids subsetting, and bit 9 (`0x0200`) allows bitmap
embedding only. For OS/2 table versions 0 to 2, more than one of bits 0–3 may
be set, and the least restrictive permission takes precedence. From version 3
they are mutually exclusive.

**Quoted** from the OS/2 chapter of OpenType 1.9.1 (Microsoft Learn, "OS/2 —
OS/2 and Windows metrics table (OpenType 1.9.1)", page dated 2024-05-29),
"Comments":

> Bits 0 to 3 (the embedding permissions sub-field) are mutually exclusive:
> fonts should never have more than one of these bits set. Note that, if two
> or more bits are set, some applications could assume the least-restrictive
> permission indicated. (See version differences for more discussion.)
> Caution: Font vendors are responsible to set these bits correctly to obtain
> the desired application behaviors. For Restricted License embedding to take
> effect, the Embedding permissions sub-field must have the value 2 (that is,
> only bit 1 is set).

and "Version differences":

> Versions 0 to 2: The specification for versions 0 to 2 did not specify that
> bits 0 to 3 must be mutually exclusive. Rather, those specifications stated
> that, in the event that more than one of bits 0 to 3 are set in a given
> font, then the least-restrictive permission indicated take precedence. In
> particular, some fonts using a version 0 to version 2 OS/2 table have both
> bit 2 and bit 3 set with the intent to indicate both preview/print and edit
> permissions. Applications are permitted to use this behavior for fonts with
> a version 0 to version 2 OS/2 table.
>
> Versions 3 and later: The specification for version 3, added in OpenType
> 1.4, introduced the explicit requirement that bits 0 to 3 must be mutually
> exclusive.

The same chapter says bit 0 "is permanently reserved and must be zero".

**The level an editable field needs** is **Editable (8) or Installable (0)**.
Filling a field formats new text with the embedded font and saves it, which is
the Editable definition. Preview & Print forbids it.

**What Tincture checks today.** `fs_type_restrictions/2`
(`lib/tincture/pdf.ex:1185-1193` at `416a9db`) flags:

- `0x0002`, Restricted License;
- `0x0200`, bitmap only;
- `0x0100`, no subsetting, unless the font is registered with `subset: :none`.

By default these are warnings (`warn_embedding_permissions_if_needed/5`,
`pdf.ex:1095-1136`). With `enforce_embedding_permissions: true` they raise
(`enforce_embedding_permissions!/5`, `pdf.ex:1138-1183`). Both run at
registration (`register_embedded_font/6`, `pdf.ex:1014-1043`). Preview &
Print (`0x0004`) and Editable (`0x0008`) are not distinguished. The OS/2
version is read (`lib/tincture/font/ttf.ex:75`, `:882`).

**A defect in that reading.** The `0x0002` test reads bit 1, not the
permission value. A version 0–2 font with `fsType` 10 (bits 1 and 3) or 6
(bits 1 and 2) is flagged as Restricted License, although the quotation above
makes it Editable or Preview & Print, and Restricted License takes effect only
for the value 2. The result is a wrong warning by default, or a wrong refusal
with `enforce_embedding_permissions: true`.

**Decision (stage 5a plan, 2026-10-21): one reading of the permission.**
Stage 5a adds one function that reads the permission sub-field, and both the
editable-field check and registration use it, so the codebase never holds two
interpretations of `fsType`:

- bit 0 is ignored, as permanently reserved;
- no bit of 1–3 set: Installable;
- OS/2 version 0 to 2: the least restrictive of the bits set (Editable, then
  Preview & Print, then Restricted License), as the quotation permits;
- OS/2 version 3 and later: more than one bit set is invalid, and is read as
  the most restrictive bit set, the conservative reading of "mutually
  exclusive" for a licence check;
- no OS/2 table: Installable, as registration treats it today.

At registration this is more permissive exactly where the specification says
it should be: a version 0–2 font combining bits. It is a fix to released
behaviour, in a self-contained commit, listed under `### Fixed`, and
backported in 0.3.8 (section H).

**Decision.**

- An editable field whose embedded font has a usage permission of 2 or 4, or
  bit 9 set, raises `ArgumentError` at the field call, **whatever
  `enforce_embedding_permissions` says**:

  ```
  text field "full_name" uses the embedded font "Body", whose OS/2 fsType (4)
  allows Preview & Print embedding only. Filling a form field formats new
  text with the font, which needs Editable or Installable embedding. Use a
  font licensed for editable embedding, or make the field read_only: true.
  ```

- The permission is the one reading above: for an OS/2 table of version 0
  to 2 with several of bits 1–3 set, the least restrictive applies; for
  version 3 and later, several bits are read as the most restrictive; no
  OS/2 table is Installable.
- Bit 8 (no subsetting) does not block an editable field: neither
  `full_font: true` nor `subset: :none` subsets.
- Read-only and non-editable fields keep today's registration-time behaviour.
- The refusal is not configurable. `enforce_embedding_permissions: false`
  keeps its meaning for drawn text, where the document is read-only. A form
  that invites edits a font's licence forbids is a different statement.
- This is new API only: embedded fonts on fields are refused today.

Whether veraPDF checks `fsType` at all: no rule in `PDFA-2B.xml`,
`PDFA-2U.xml`, `PDFA-2A.xml` or `PDFUA-1.xml` mentions it. So this refusal has
no validator evidence, and is tested by unit tests only.

### The `/DA` font

The font dictionary that `/DR` carries for an editable field decides which
characters a viewer can draw when it regenerates the appearance.

**Decision (stage S, 2026-10-20).** **Option (b): the `Type0` `/Identity-H` font.**

- **The dictionary.** `/DR` names the same `Type0` dictionary that page text
  uses: `/Identity-H`, a `CIDFontType2` (or CFF) descendant, a `ToUnicode`
  CMap, and the whole font program (section C's full-embed decision). A font
  whose page text is all 7-bit ASCII is written today as a simple `/TrueType`
  font (current behaviour above). **Decision (stage 5a plan, 2026-10-21):
  when such a font is also a field font, it becomes `Type0` everywhere.**
  Page text in it is encoded through Identity-H, and there is one font
  dictionary and one font program, named by both the page's `/Font` and
  `/DR`. This replaces the earlier plan of a second, `Type0` dictionary
  written for `/DR` beside the page's simple one: a single dictionary needs
  no second family builder over a shared program, and raises no question of
  a descriptor shared between a simple and a CID font. Only documents with
  an embedded field font are affected, and those are refused before 0.4.0.
- **Discovery.** A font used only by fields is still discovered and embedded.
  Font discovery is given one synthetic operation list per embedded-font
  field, keyed `{:field, name}`, holding the strings the font must draw: the
  value and every option of a non-editable field, the value of an editable
  one. They are not content streams and are not written.
  - **Decision (stage 5b plan, 2026-10-23).** Stage 5b replaces them with the
    appearance streams' own operation lists, for the text an appearance
    draws.
  - A `{:field, name}` list **stays** for each non-editable choice field, for
    the options no appearance draws. A combo box draws only its selected
    value, but the subset must still hold every option's glyphs ("Which
    fields are editable", above), since a viewer draws the option someone
    picks.
- **Editable values are not restricted to WinAnsi.**
- **Evidence: observed, on screen.** In both Acrobat and Chrome, the `Type0`
  file of stage S question 1 showed both `Größe` and `Ελλάδα` correctly while
  typing. That meets the selection rule for (b). The simple-font file did too.
  The byte-level confirmation for the `Type0` file was missing. The stage 5b
  proof supplied it, and it is **mixed**:
  - pdf.js regenerates a typed Greek value with the `/DR` `Type0` font;
  - PDFium uses that font for Latin text, and for Greek adds a non-embedded
    font of its own.

  See section D, "Known limitation: PDFium substitutes its own font".
- **What a viewer does with it.** The one saved file from the spike, a
  simple-font file, shows the viewer drew the WinAnsi part of the value with
  the `/DA` font and embedded a `Type0` subset of its own for the rest. With
  (b) the `/DA` font already covers every character the font program has.

**Dropped with option (a).** Three things existed only under option (a), and
are not built:

- the simple WinAnsi `/DR` font variant carrying codes 128–255;
- the WinAnsi restriction on embedded-font editable values;
- the refusal of editable fields with CFF (OpenType) fonts. The `Type0` path
  already serves CFF.

**One font dictionary and one font program per font.** A font used by an
editable field is embedded whole, through `full_font: true` or
`subset: :none` (above). `full_font: true` makes the font whole for the
whole document through a set of font names passed to font embedding; the
registered `subset:` in the document struct is not changed. If the same font
also draws page text, the page's `/Font` resource and `/DR` name **the same**
`Type0` dictionary over **the same** whole font program: one `FontFile2` (or
`FontFile3`) object, not a subset for the page plus a whole copy for the
field. The size consequence, stated once: page text in that font carries the
whole program, which the caller already chose by making the field editable.

**Decision (stage 5a plan, 2026-10-21): an editable field's font covers its
whole cmap.** Page text builds `/W`, the `CIDToGIDMap` and the `ToUnicode`
CMap from the characters the document draws. For a font used by an editable
field, a character typed later would be in the program but in none of the
three: no glyph mapping, no width, no Unicode mapping. So for such a font all
three cover every codepoint of the font's cmap. Measured on the vendored
Liberation Sans: 2326 cmap entries, all in the Basic Multilingual Plane, for
a 411860-byte program; the `CIDToGIDMap` stream is Flate-compressed, and `/W`
holds at most 2326 widths.

**Whether viewers use these entries when someone types: observed in the stage
5b proof.** pdf.js does. PDFium does not for Greek, and uses a font of its own
(section D, "Known limitation").

**Decision (2026-10-30): option (b) stands for Acrobat Reader, and editable
embedded-font fields stay in 0.4.0.** The `/DR` entry is the shared, indirect
`Type0`/Identity-H dictionary, `/DA` names it, and the field's `/AP` references
the same object. An auto-sized field names its resolved size in `/DA`
(section D, "The `/DA` size of an embedded-font field").

The question arose in the stage 5b calibration (Acrobat Reader
2026.002.22031, 2026-10-23). With the `/DR` fonts indirect (0.3.11), every
standard-14 field kept a typed value. A field whose `/DA` font is this
`Type0`/Identity-H dictionary, over the whole Liberation Sans program,
discarded it when the field lost focus, and Acrobat wrote no appearance for
it. Stage S's evidence for option (b) had been seen while typing, not after
the field lost focus.

**The evidence that settles it,** in the same Reader build, each file typed
into, saved, closed and reopened:

- **One property at a time, on stage 5a's output.** A single embedded-font
  text field, `/DA (/Sans 12 Tf 0 g)`, with `/NeedAppearances true` and no
  `/AP`, and six variants each changing one property:
  - a simple `TrueType`/WinAnsi font in place of the `Type0`;
  - no `ToUnicode`;
  - `/CIDToGIDMap /Identity`;
  - a partial `/W`;
  - the font's PostScript name as `/BaseFont`;
  - an `/AP`.

  **All eight files kept a typed Latin and Greek value.** The saved files
  show why the variants made no difference. Reader writes its own
  appearance: Latin through a simple re-encoding of the embedded program
  that it adds to `/DR`, and Greek through a `Type0` subset of that same
  program. None of the varied properties is read for drawing.
- **The document as 0.4.0 writes it.** This is stage 5b's review document,
  with the `/DR` fonts indirect, an `/AP` on every widget, and no
  `/NeedAppearances`. An embedded-font field and a Helvetica field both kept
  a typed Latin and Greek value.
- **At auto size, a Latin-only edit is not redrawn.** In that document, the
  embedded-font field at `/DA (/Sans 0 Tf 0 g)` was given `Hello`.
  - Reader stored `/V (Hello)`, but kept Tincture's appearance of the old
    value: no stream in the saved file draws `Hello`.
  - The same file with `/DA (/Sans 14.897 Tf 0 g)`, the size of Tincture's
    own appearance, was redrawn.
  - Section D, "The `/DA` size of an embedded-font field", is the rule this
    gives.
- **The calibration's discarded value is not explained.**
  - That file had no `/AP` and had been edited by script after Tincture
    wrote it.
  - No single property of it, added to the probe's base, reproduced the
    loss, and nor did auto size with a Greek starting value.
  - The 0.4.0 review document, as Tincture writes it, does not show the
    loss.
  - Investigating it further is out of scope.

Section E's archival form, which allows only embedded field fonts, rests on
this decision.

**Out of scope here: standard-14 fields.** A standard-14 font remains
WinAnsi, so J4 stands (below).

### Standard-14 fonts on fields

A standard-14 field font is written in `/DR` with `/WinAnsiEncoding`
(`serialize.ex:775`). A generated appearance can only draw characters that
encoding contains. So in 0.4.0:

- a text or choice field with a standard-14 font, whose value or any option
  contains a character outside WinAnsi, raises `ArgumentError` at the field
  call;
- the same applies to a push button's `:label`.

This holds whatever the `/DA` font of embedded fonts, and it breaks code that
works on 0.3.4, where such a value is written as `/V` and left to the viewer
(section J, item J4). The appearance text is written as WinAnsi bytes, not
through the page-text path described above.

**Decision (stage 5b plan, 2026-10-23): how.**

- **A `:win_ansi` text mode** in `Object.encode_text/2` maps each codepoint
  through `WinAnsi.code/1`, and writes an escaped literal string, with octal
  escapes for bytes 128 and above: `"Größe"` becomes `(Gr\366\337e)`.
  - **0.3.10 introduces it**, to fix the push-button caption. Up to 0.3.9 a
    label such as `"Größe"` was written as UTF-16BE (`<FEFF0047…>`) under a
    font whose `/Encoding` is WinAnsi, so it showed the wrong glyphs.
  - 5b uses it for every standard-14 appearance. The page-text path never
    asks for it, so page bytes do not change.
- **The appearance's font resource is the `/DR` dictionary under the `/DA`
  alias.**
  - For a standard font: `/Helv << /Type /Font /Subtype /Type1 /BaseFont
    /Helvetica /Encoding /WinAnsiEncoding >>`, as in `/DR`.
  - For an embedded font: the `/DR` reference to the `Type0` dictionary.
  - Not `/F1` from `font_resources/2`. That function writes no `/Encoding`
    for a standard font, and its output format does not change (above).
  - The content stream writer takes the aliases as an argument, so no new
    resource collector is needed.

### Bytes

The `/DR` of a form whose editable fields use an embedded TTF font registered
as `"Body"` with `full_font: true`:

```
/AcroForm << /Fields [20 0 R 23 0 R] /DA (/Helv 0 Tf 0 g) /DR << /Font << /Body 31 0 R >> >> >>

31 0 obj
<< /Type /Font /Subtype /Type0 /BaseFont /Body-Regular /Encoding /Identity-H /DescendantFonts [32 0 R] /ToUnicode 34 0 R >>
endobj

32 0 obj
<< /Type /Font /Subtype /CIDFontType2 /BaseFont /Body-Regular /CIDSystemInfo << /Registry (Adobe) /Ordering (Identity) /Supplement 0 >> /FontDescriptor 33 0 R /W [...] /CIDToGIDMap /Identity >>
endobj
```

- `33 0 R` carries `/FontFile2` pointing at the whole program.
- With a full embed, the `/BaseFont` has no subset tag. With a subset it has
  one (`ABCDEF+`).
- **The subset-tag rule** (ISO 32000-1 9.6.4, fixed on `fix-subset-tag`,
  2026-11-05): the tag on `/BaseFont` and `/FontName` is written **if and
  only if the embedded font program is a subset**, that is, differs from the
  registered font's bytes. Before the fix it followed the `:subset` option
  alone, so a font that subsetting fell back to embedding whole was still
  tagged. The fallbacks, in `lib/tincture/pdf/font_embed.ex` at `5c320ab`:
  - TrueType: a composite glyph naming a component the font lacks (`:431`),
    or whose component records do not parse (`:438`); a subset no smaller
    than the font, or a failed sfnt rebuild (`:441`); no `glyf` or `loca`,
    or an unusable `loca` (`:445`);
  - OpenType: a `CFF ` table that cannot be subset, or a subset no smaller
    (`:489`); no `ttf_metrics` (`:493`), unreachable since stage 1e.

  No committed example reaches a fallback, and every example is
  byte-identical with the fix: the examples' Liberation fonts are real
  subsets and keep their tags.
- The alias `/Body` is `Object.sanitize_name/1` of the registered name, as
  `acro_form_font_alias/1` already does for standard fonts
  (`serialize.ex:781-782`).
- The AcroForm-level `/DA` is described in section D. In a PDF/A document it
  is not written (section E).

## D. Appearance streams

### Decision: every widget gets `/AP /N`

`/NeedAppearances` is never written: `acro_form_entry/2`
(`serialize.ex:745-750`) loses the branch. `PDFA-2B 6.4.1-3` requires the flag
to be absent or false. `PDFA-2B 6.3.3-1` requires an appearance dictionary on
every annotation except zero-size ones, Popup and Link.

**The shape of `/AP`** follows `PDFA-2B 6.3.3-2` to `6.3.3-4`, which Tincture
then meets for every document, not only archival ones:

- **only `/N`**, no `/R` or `/D` (`6.3.3-2`);
- **for `/FT /Btn`** (checkbox, radio, push button), `/N` is a subdictionary
  of named states (`6.3.3-3`). Checkboxes and radio buttons write one. The
  push button writes a stream (`push_button_appearance_object_body/1`), and
  keeps it: no PDF/A document can hold a push button (section E). That is
  examined in its own subsection below;
- **for every other field type**, `/N` is a stream (`6.3.3-4`).

### Text fields

**What the standard fixes, and what it leaves open.** ISO 32000-1 §12.7.3.3
(pages 434–436, **quoted**) fixes the following:

- the appearance's form dictionary: "The resource dictionary (Resources)
  shall be created using resources from the interactive form dictionary's DR
  entry", and `/BBox` is `[0 0 w h]` from `/Rect`;
- the marking: the text is drawn inside `/Tx BMC … EMC`;
- the `/DA` rule: "The specified font value shall match a resource name in
  the Font entry of the default resource dictionary".

The reason for the marking is on page 436: an updating reader "shall then
replace the existing contents of the appearance stream from /Tx BMC to the
matching EMC". Anything outside the marking survives an edit. No veraPDF
rule checks the marking.

The standard does not fix any of the following, so the rules below are the
design's own:

- vertical placement, padding or leading: a reader positions text by "any
  layout rules it employs" (page 435);
- the auto size: "its size shall be computed as a function of the height of
  the annotation rectangle", with no formula (page 435).

**Decision (stage 5b calibration, 2026-10-23): the geometry follows Acrobat
Reader.** The stage 5b plan's own rules (an inset clip, `TextExtent`'s
0.75/0.25 metrics, a 1.15 leading and a 12-point cap) failed the visual
review. They are replaced by what Adobe Acrobat Reader 2026.002.22031 writes
for the same fields, measured from the appearance streams it saved.
"Calibration: what was measured", below, gives the method, the six
residuals, and what was not measured. **Evidence: observed**, for Helvetica
fields only.

For a widget `w × h` whose `:border` width is `b` (0 for `border: :none`):

- **No clip, and no `q … Q`.** Acrobat writes only `/Tx BMC … EMC` around
  `BT … ET`. The form XObject's `/BBox [0 0 w h]` clips.
- **Padding** `p = 2b`. Measured: text starts at x 0 with no border, and at
  4 with `/Border [0 0 2]`.
- **The line box and the descender.** A line of text occupies a box
  `L = s × line` tall, where `line` is the font's bounding-box height per em.
  Its baseline is `s × descent` above the box's bottom, where `descent` is
  the font's descender per em. For Helvetica, `line` = (931 + 225)/1000 =
  1.156 (AFM `FontBBox`) and `descent` = 0.207 (AFM `Descender`). Measured:
  list rows and multiline leading 13.872 at size 12 (12 × 1.156), and list
  baselines 2.484 above the row (12 × 0.207).
- **Where the metrics come from:**
  - for the standard 14, the AFM `FontBBox` and `Descender`
    (`Font.Standard`, all 14);
  - for a TrueType or OpenType font, head's bounding box over `unitsPerEm`,
    and OS/2 `sTypoDescender`, else hhea `descender`;
  - when neither is available, Helvetica's values.

  **Only Helvetica was measured.** For a TTF, the choice of OS/2 over hhea,
  and the bounding box as the line, are unmeasured: the one embedded-font
  field in the calibration produced no Acrobat appearance (section C, "The
  `/DA` font").
- **Colour.** The text is black, written as `0 0 0 rg` before `BT` through
  the existing `set_fill_color` operation. Acrobat writes `0 g`, the same
  colour (residual 6).
- **The border**, when `b > 0`, is stroked **before** `/Tx BMC`, so that an
  editing viewer keeps it: `0 0 0 RG b w (b/2) (b/2) (w − b) (h − b) re S`.
  Acrobat draws no border for `/Border [0 0 2]` without `/MK /BC`
  (residual 3). Tincture strokes the `:border` it was given, so the option
  keeps its meaning; only the padding follows Acrobat. **The widget declares
  the border** in `/MK /BC` and `/BS /W` (decided 2026-10-30; see "`/MK`,
  JavaScript and flattening").
- **The font** is the `/DR` font, under the `/DA` alias (section C,
  "Standard-14 fonts on fields"). So the `Tf` in the stream is the `/DA`'s
  own, and a reader merging `/DR` into the stream's resources on update finds
  matching names (page 436).
- **The marking** is written around the operations as literal strings. Every
  operation inside it is an existing one, so the public `op()` type does not
  change.

**Single line.**

- **Baseline.** The line box is centred in the field:
  `y = (h − L)/2 + s × descent`. Measured: 4.9524 at size 16.302 and 7.6615
  at size 9 in a 22-point field, and 6.0536 at 13.334 in an 18-point field
  with a 2-point border. Each is within 0.002 of the rule.
- **`/Q` quadding.** A new `:align` option takes `:left` (0, the default),
  `:center` (1) or `:right` (2). It is written as `/Q` on the field, except
  for `:left`, which is the default (Table 222). In the appearance, `x` is
  `p`, `(w − width)/2` (centred on the full width) or `w − p − width`, where
  the width is the font's measured text width. Measured in a 240-point
  field at 16.302: 91.008 for "Centred", and 176.568 for "1,234.50".
- **A value wider than `w − 2p`** shrinks the auto size to fit (below). At a
  fixed size it is drawn from `x` and clipped by the `/BBox`, not truncated or
  scaled.

Bytes for `"Ada Lovelace"` in Helvetica, in a 200 × 24 widget at auto size,
as stage 5b writes them: `s` = 24/(1.156 + 2 × 0.0968) = 17.783, and
`y` = (24 − 17.783 × 1.156)/2 + 17.783 × 0.207 = 5.4025.

```
/Tx BMC
0 0 0 rg
BT
/Helv 17.783 Tf
0 5.4025 Td
(Ada Lovelace) Tj
ET
EMC
```

The stage 5b plan's example here (`q`, a `1 1 198 22 re` clip, `/Helv 12 Tf`,
`2 9 Td`) followed the plan's rules, which the calibration replaced.

**Font size 0 (auto).** **Decision (stage 5b calibration, 2026-10-23).**

- **Single line and combo box:** `s = (h − 2b)/(line + 2 × 0.0968)`. If the
  value measured at `s` is wider than `w − 2p`, then
  `s = s × (w − 2p)/width`, floored at 4.
  - **0.0968 is fitted, not taken from the font.** It is the margin, in
    ems, above and below the line box. It is the one constant fitted to
    Acrobat's two measured sizes: 16.302 for `h − 2b` = 22, and 13.334 for
    18. The rule gives 16.301 and 13.337.
  - For `"Ada Lovelace"` at 200 × 24: 17.783, and the value (107.7 wide)
    fits in 200.
- **Multiline:** start at 12, and step down by 0.5 until the wrapped lines'
  boxes (`lines × L`) fit `h`, with a floor of 4. Below the floor the text is
  clipped.
  - Measured: Acrobat used 12 where the text fits.
  - The 0.5 step and the floor are the design's own and unmeasured.
- **List box:** 12. Measured.
- **A fixed size is never changed.**

Viewers may compute auto size differently when they regenerate: PDFium uses
18 where Acrobat uses 16.302 ("Calibration", below). The value written is
the size Tincture computed. `/DA` keeps `0 Tf`, so an editing viewer still
auto-sizes.

**Standard-14 text** in an appearance is written as WinAnsi bytes
(section C).

**Multiline** (`multiline: true`):

- **Wrapping.** The value is broken at `\r\n`, `\n` and `\r`, and each
  paragraph is then wrapped greedily at spaces to `w − 2(p + 2)`. A single
  word wider than that is clipped, not broken.
  - **The wrap width is bracketed, not pinned** (residual 4). At size 12 in a
    500-point field, Acrobat kept a line 486.348 wide (with its trailing
    space) and broke before one 499.692 wide. 496 is the round value inside
    that bracket.
  - **Decision (stage 5b plan, 2026-10-23): spaces and line breaks**, not line
    breaks only. A viewer that lets someone edit the field wraps at the box
    width, and the generated appearance should look like what the user will
    see after editing.
  - The Knuth-Plass engine is not used.
- **Layout.** The leading is the line box, `L = s × line`. The first baseline
  is at `h − L`, and each following line is `L` lower. Measured: leading
  13.872 at size 12, and a first baseline at 42.128 in a 56-point field.

**Password fields. Decision (2026-10-30): the appearance is empty.**

- The appearance draws no text, whatever the value: `/Tx BMC EMC`, with the
  border before it if `b > 0`. This is what the stage 5b plan ruled and
  stage 5b writes.
- Acrobat and PDFium both draw one asterisk per character (residual 2).
  Tincture does not follow them here: an empty appearance does not show the
  value's length.
- The value itself is in the file as `/V` either way, which is the current
  behaviour, and the `@doc` says it is readable by anyone who opens the
  file.

ISO 32000-1 Table 228, page 443, **quoted**, NOTE to the Password flag: "To
protect password confidentiality, readers should never store the value of the
text field in the PDF file if this flag is set." It is addressed to readers,
not writers.

**Comb fields: out of 0.4.0.** No current option creates one: there is no
comb flag in `field_flags/2`. They need a `/MaxLen` cell layout, and nothing
in the release depends on them.

### Choice fields

**What the standard says about choice appearances: nothing.** ISO 32000-1
§12.7.4.4 (pages 444–446) defines the flags, `/Opt`, `/TI`, `/I` and `/V`,
and no drawn appearance. A `/Ch` field is a variable-text field, so
§12.7.3.3's rules (text fields, above) are the only ones that apply. The
layouts below are the design's own. The geometry, font and marking are the
text fields'.

**Combo box** (`dropdown: true`, editable or not). The appearance is that of
a single-line text field showing `/V`, or `/Tx BMC EMC` when there is none.

- `/V` is shown even when it is not one of the options. A non-editable field
  with such a value is warned in 0.3.10 (W8) and refused in 0.4.0
  (section J).
- No drop-down arrow is drawn. Viewers draw their own while the field has
  focus.
- **Unmeasured** (residual 5). Acrobat drew both dropdowns but wrote no
  appearance for them, so the combo box uses the single-line rules. PDFium
  draws a drop-down button into its appearance; Tincture does not.

**List box** (`dropdown: false`):

- **Rows.** Options are drawn top to bottom, one per row, in `/Opt` order.
  - That is the order a reader shows. Table 230, **quoted**: "Conforming
    readers shall display the options in the order in which they occur in
    the Opt array".
  - From 0.3.10, `sort: true` writes `/Opt` sorted (section H).

### Calibration: what was measured

**Method.** In Adobe Acrobat Reader 2026.002.22031 (Continuous Release,
64-bit, Windows), the review document's text and choice fields were drawn by
Acrobat, saved, and their appearance streams read back:

- the fields were Helvetica, `/DA (/Helv 0 Tf 0 g)` unless a size was set;
- the single-line fields were 240 × 22, and the bordered one 240 × 18 with
  `/Border [0 0 2]`;
- the multiline field was 500 × 56, and the list boxes 240 × 50.

Every rule above that says "measured" comes from those streams.

**Only Helvetica was measured.** The embedded-font field produced no Acrobat
appearance (section C, "The `/DA` font"). So, for a TrueType or OpenType
font, the bounding box as the line and OS/2 `sTypoDescender` over hhea
`descender` are unmeasured.

**After the calibration**, Tincture minus Acrobat: size within 0.003, x
within 0.012 (the right-aligned field), first baseline within 0.002, and
multiline and list spacing exact.

**The six residuals:**

1. **The list-box band** sits one row (13.872) lower than Acrobat's. In
   Acrobat the review's clicks selected a different option than the file's
   `/V`. The band's geometry and colour match.
2. **Password.** Acrobat and PDFium draw one `*` per character; Tincture
   draws nothing. Decided: empty ("Password fields", above).
3. **Border.** For `/Border [0 0 2]` with no `/MK /BC`, Acrobat draws no
   border in the appearance. Tincture strokes the `:border` it was given,
   and only the padding follows Acrobat. Decided: the widget declares the
   border in `/MK /BC` and `/BS /W` ("`/MK`, JavaScript and flattening",
   below).
4. **The multiline wrap width** is bracketed between 486.35 and 499.69 in a
   500-point field, not pinned. The rule uses 496.
5. **The dropdowns** have no Acrobat appearance, and use the single-line
   rules. PDFium draws a drop-down button; Tincture does not.
6. **Text colour** is written `0 0 0 rg` against Acrobat's `0 g`. The colour
   is the same.

**Where Acrobat and PDFium disagree, Acrobat is followed.**

### Signature fields

**Visible** (non-zero rectangle):

- `/N` is a stream.
- **The border.** With `:border`, the appearance strokes the border whether
  or not the field has a `:label`, as an empty bordered text field does:
  `0 0 0 RG b w (b/2) (b/2) (w − b) (h − b) re S`, and a label is padded by
  twice the width. **Decision (2026-10-30).**
- **Without `:border` and without `:label`,** the content is empty:
  `<< /Type /XObject /Subtype /Form /BBox [0 0 w h] /Resources << >> /Length 0 >>`,
  written through `form_xobject` as every widget appearance is. An empty
  stream is still an appearance, which is what `PDFA-2B 6.3.3-1` requires.
  Signing in `sign/3` changes neither.
- **`:label`**, a new `signature_field/7` option, draws one line of text,
  left-aligned, laid out like a single-line text field: for example "Signed
  by A. Lovelace".
  - **Its size. Decision (2026-10-30), option (a):** without `:size`, the
    label follows the single-line auto-size rule, like every other field: it
    fills the field's height and shrinks to fit the width. There is no
    second rule. The `@doc` and the example recommend an explicit `size:` of
    10 to 12 for a signature line, since a label that fills a 44-point field
    is drawn at about 24 points.
- No graphic or image is drawn. That is out of scope (section I).

**Invisible.** **Decision (stage S, 2026-10-20).** **Kept, and owned by a `Form` element,
like any other widget.** A new `invisible: true` writes `/Rect [0 0 0 0]`
and no `/AP`.

- **The position arguments.** With `invisible: true`, all four of
  `signature_field/7`'s `x`, `y`, `width` and `height` must be 0, so the
  `/Rect` written is exactly what the caller passed and no argument is
  silently ignored. It is stored as that zero rectangle, with no new key in
  the field. **Decision (2026-10-30).**
- **Two refusals,** raised at the call, before J4, in this order:
  - `invisible: true` with `:label`: "signature field "sig" is invisible:
    true and has a :label. An invisible signature has no appearance to draw
    the label in. Remove the :label, or drop invisible: true."
  - `invisible: true` with any non-zero position argument: "signature field
    "sig" is invisible: true, but was given the rectangle x 72, y 600, width
    200, height 40. An invisible signature's rectangle is [0 0 0 0]: pass 0,
    0, 0, 0, or drop invisible: true."

- **PDF/A.** `PDFA-2B 6.3.3-1` exempts a zero-size rectangle: "the value of
  the Rect key consists of an array where value 1 is equal to value 3 and
  value 2 is equal to value 4".
- **PDF/UA.** The widget has a `Form` element, `/StructParent` and a
  `/ParentTree` entry, as section F gives every widget.
- **`/F`.** It keeps `/F 4` (Print), as `PDFA-2B 6.3.2-2` requires print set
  and hidden clear.
- **Evidence: observed.**
  - veraPDF 1.30.2 passes the `Form`-owned file in full, at PDF/UA-1 and
    PDF/A-2b.
  - PDFgear on Windows 11 (version not recorded) lists the unsigned field in
    its signature panel and draws nothing on the page. PDFgear stood in for
    Acrobat. A signing tool listing the field is the property this check
    asks for.
- **A validator blind spot.** veraPDF also passes the same widget with no
  `Form` element, because it treats `/Rect [0 0 0 0]` as outside the crop
  box. That exempts the widget from `PDFUA-1 7.18.4-1` and `7.18.1-3`, so a
  missing `Form` element on an invisible signature is invisible to veraPDF.
  The structure tests of section F are what catch it.

`invisible: true` is new API, so this is backward compatible.

The signature dictionary, the `/ByteRange` and the `/Contents` do not change
(`Sign.placeholder_dictionary/1`, `Sign.apply_signature/2`).

### Checkbox, radio and push button

- **Checkbox and radio** are unchanged in output. They draw no text and use no
  font.
  - Their builders change from strings to operation lists, as section B
    requires.
  - Their appearance bytes are pinned by the existing tests, and must not
    move.
- **The push-button caption** stops writing an inline `/Helv` Type1
  dictionary (`push_button_caption/3`).
  - Its font resource follows the widget font rule ("`/DA` and `/DR`",
    below): the document's one object for the field's `:font`, standard or
    embedded, under the field's `/DA` alias.
  - With a standard font the caption bytes are unchanged, and the resource
    becomes a reference to `/DR`'s font object rather than an inline
    dictionary. That change is listed in the CHANGELOG (section J).
  - **Stage 6b.** In stage 6a the caption keeps its inline `/Helv` through a
    single override in `widget_stream`, so that 6a changes no byte.
- **The push button declares what its appearance draws. Decision
  (2026-10-30).**
  - Beside `/MK /CA`, every push-button widget writes `/MK /BG`, the face's
    fill colour, `/MK /BC`, the frame's stroke colour, and `/BS /W`, the
    frame's width: `/MK << /BC [0.55 0.57 0.6] /BG [0.93 0.93 0.94] /CA … >>`
    and `/BS << /W 0.75 >>`. Each is taken from the appearance's own
    operations, as a text field's `/BC` is, so the declaration and the
    drawing cannot disagree. Nothing else from `/MK` is written.
  - **The `/DA` names the size the caption is drawn at, for every font,**
    standard or embedded, never `0`.
  - **Why.** In Acrobat Reader 2026.002.22031 (2026-10-30), a push button
    showed Tincture's appearance at rest. But when it lost focus, after
    being pressed, or when the form was reset, Reader drew it anew from
    what the widget declares:
    - with no `/MK /BG` or `/BC` it lost its grey face and frame;
    - with `/DA` at `0 Tf` it drew the caption at a size of its own, much
      larger in a Helvetica button;
    - a caption in an embedded font, whose `/DA` already named its size
      (5b's rule), kept the size and lost face and frame.

    This is the same mechanism as the text field's border (section D,
    "`/MK`, JavaScript and flattening"). In 0.3.12 the buttons were drawn in
    Reader's own style from the start, since the form carried
    `/NeedAppearances`; stage 6b's are the first to show Tincture's
    appearance at rest.
  - **PDFium (156)** draws the face from `/MK /BG` when it regenerates a
    push button, and no face without it. It draws no frame in any variant
    tried: `/BS /W` at 0.75, 1 and 2, `/Border` at 0, 0.75 or absent, and
    `/BS /S /S`. The Viewer job requires the face and reports the frame.

**The push button's `/N` stays a stream. The earlier decision to make it a
subdictionary is withdrawn (2026-10-30).**

- **Today.** `push_button_appearance_object_body/1` writes one stream, so
  `/AP << /N 25 0 R >>` holds a stream. `PDFA-2B 6.3.3-3`: "If an annotation
  dictionary's Subtype key has a value of Widget and its FT key has a value
  of Btn, the value of the N key shall be an appearance subdictionary".
- **Why it is withdrawn:**
  - No PDF/A document can hold a push button. `push_button/7` requires
    `:action`, written as `/A`, and `PDFA-2B 6.4.1-1`: "A Widget annotation
    dictionary shall not contain the A or AA keys". A `:reset` action is
    also forbidden by `6.5.1-1`: "The Launch, Sound, Movie, ResetForm, …
    actions shall not be permitted". Section E keeps the refusal.
  - ISO 32000-1 models a pushbutton's appearance as streams. The FDF field
    dictionary's `/AP` (12.7.7) is "an appearance dictionary specifying the
    appearance of a pushbutton field … The appearance dictionary's contents
    are as shown in Table 168, except that the values of the N, R, and D
    entries shall all be streams."
  - A subdictionary needs `/AS` (Table 164: "Required if the appearance
    dictionary AP contains one or more subdictionaries"), so the change
    would add an `/AS` and a state name, `/Default`, that nothing uses.

### `/DA` and `/DR`

- **`/DA` stays on every widget**, as today (`form_field_object_body/4`), except in
  a document that declares PDF/A, where only a field that draws text with a
  font carries it: text and choice fields, and a labelled signature
  (section E, as decided for stage 7).
- **`/DR /Font`** lists the fonts named by the fields' `/DA`, under the alias
  used there, as today (`build_dr_font_objects/3`, `acro_form_font_resources/1`).
  An embedded font appears as the `Type0` dictionary section C decides, and a
  standard font as today.
- **The AcroForm-level `/DA`** (`default_appearance_entry/1`) is
  `/Helv 0 Tf 0 g`. It is written only when `/DR`
  holds `/Helv`, that is, when some field uses Helvetica. It is not written in
  a document that declares PDF/A (section E). Every widget carries its own
  `/DA`, so the document-level default is never the one used.
  - **The defect this fixes, shipped in 0.3.10.** Up to 0.3.9 the AcroForm
    `/DA` was written whatever `/DR` held. A form whose fields all use another
    font, such as Courier or, since stage 5a, an embedded font, named a
    `/Helv` that `/DR` did not contain.
  - ISO 32000-1 §12.7.3.3, page 435, **quoted**: "The specified font value
    shall match a resource name in the Font entry of the default resource
    dictionary". Table 218, page 431, makes the AcroForm `/DA` "a
    document-wide default value for the DA attribute of variable text
    fields", so the rule applies to it.
  - Omitting it is allowed: the key is optional (Table 218).
- **Consistency is a test.** For every widget with `/DA`, the font alias it
  names resolves in `/DR`. For text and choice widgets, the same font object
  is used by that widget's `/AP` stream resources.
- **One object per font.** Every `/DR` font is an indirect object: a
  standard font gets one `Type1`/WinAnsi object of its own (0.3.11), and an
  embedded font is the page text's `Type0` object. Each appearance stream's
  `/Resources` references that same object, never an inline copy.
- **The widget font rule. Decision (2026-10-30).** Every widget appearance
  (text, choice, checkbox, radio, push button, signature) names each font it
  draws with under the field's `/DA` alias, and its `/Resources` references
  the document's one object for that font. That object is `/DR`'s; for an
  embedded font it is the page text's `Type0` object, which `/DR` names.
  - The reasons: ISO 32000-1 §12.7.3.3 gives a variable-text appearance its
    resources from `/DR`, and a viewer regenerating an appearance from
    `/DA` resolves the alias there, so one font has one name in a widget;
    one object per font, with no inline copy; and one producer,
    `widget_stream` (section B), for every widget appearance.
  - Under PDF/A it holds unchanged (decided for stage 7, section E): a
    labelled signature keeps `/DA`, so its label's font is `/DR`'s object, as
    elsewhere. The case this sentence once covered, a signature with no
    `/DA` whose label font lies outside `/DR`, no longer arises.
  - Text and choice appearances follow it since stage 5b. The push-button
    caption and the signature label follow it from stage 6b.
- **Numbering.**
  - The `/DR` standard fonts are numbered after the metadata and before the
    info dictionary, as 0.3.11 numbers them. So a document without fields
    is numbered as before.
  - The appearance streams, written earlier with the field objects, need
    those numbers. How many objects a field takes depends only on its type:
    - a text or choice field, 2;
    - a checkbox, 3;
    - a push button, 2;
    - a radio group, 1 plus 3 per button;
    - any other field, 1.
  - So the numbering after the fields is computed first, the `/DR` fonts
    are numbered, and each field object is then built once. The serializer
    asserts the count it built against the one it computed.

**The `/DA` size of an embedded-font field. Decision (2026-10-30).** A text
or choice field whose font is embedded and whose size is auto names in `/DA`
the size its appearance resolved, written exactly as the appearance's `Tf`
operand: `(/Sans 14.897 Tf 0 g)`, not `(/Sans 0 Tf 0 g)`.

- **Standard-14 fields keep `0 Tf`.** A field with an explicit size is
  unchanged.
- **A field that draws no text,** whether empty or a password, names the
  size its box gives under the same rules: the single-line size of an empty
  value, the multiline start size, the list-box size.
- **Evidence.** In Acrobat Reader 2026.002.22031, the 0.4.0 review document
  was used, with its embedded-font field at `0 Tf`.
  - Select all, type `Hello`, and leave the field: Reader stored
    `/V (Hello)`, but wrote no appearance. Tincture's appearance of the old
    value stayed on screen and in the saved file.
  - The same file, with that one `/DA` changed to the size of Tincture's own
    appearance, 14.897, was redrawn, and saved with Reader's new appearance.
  - With Greek in the edit, Reader redrew at either size.
  - Helvetica fields at `0 Tf` were redrawn after Latin-only edits.
  - Why Reader skips the redraw is not investigated.
- **The cost.**
  - In Acrobat Reader, such a field keeps after an edit the size computed
    for its initial value. A longer value is not shrunk, and the field box
    clips it.
  - For a single-line field the size depends only on the box and the font,
    unless the initial value is too wide for the box. So what is lost is
    shrink-to-fit for long values.
  - The `:size` option's `@doc` states this. An explicit size gives full
    control.
- **Tests.**
  - The `/DA` size equals the appearance's `Tf` for a text field, a combo
    box, a multiline field and a list box.
  - A Helvetica field keeps `0 Tf`.
  - `size: 9` gives 9 in both places.
  - No embedded-font field in the committed examples, or in a document
    holding every kind, names 0.

### `/MK`, JavaScript and flattening

- **`/MK`: out, except a bordered text or choice field's `/BC`, and a push
  button's `/BG` and `/BC`.** `/MK` records border and background colours
  for a viewer to use when it regenerates an appearance. No conformance rule
  in the profiles read here requires it, and the generated appearances draw
  their own border through the existing `:border`, before the `/Tx` marking
  (text fields, above). No background is drawn for text and choice widgets,
  and nothing else from `/MK` is written for them. A push button declares
  its face and frame ("Checkbox, radio and push button", above), beside the
  `/MK /CA` it has always written.
- **Decision (2026-10-30): a bordered field declares its border.**
  - A text or choice widget with a border width `w > 0` writes
    `/MK << /BC [...] >>` and `/BS << /W w >>`.
    - `/BC` is the colour its appearance strokes the border in, with as many
      components as that colour space: `[0 0 0]`, the RGB black stroked
      today.
    - `/BS /W` is the same width.
  - `/Border` stays as written. An unbordered widget writes neither.
  - **A signature widget declares its border the same way (stage 6b,
    after review).** Its appearance strokes a border with or without a
    `:label`, with the text field's operations, so it writes the same
    `/MK << /BC [...] >>` and `/BS << /W w >>`. A signing tool that draws a
    new appearance from the widget finds the border there. A push button
    is not covered by this rule: its frame is part of its face, declared
    with it (`/MK /BC`, `/BG`, `/BS /W`, section D).
  - **Why.** A viewer that regenerates an appearance draws the border from
    these entries, not from the stroke in the old appearance. Without them,
    the calibration showed Acrobat drawing no border for `/Border [0 0 2]`
    (residual 3).
  - **PDFium shows it:**
    - filling a bordered field with `/MK /BC` and `/BS /W`, its saved
      appearance keeps the border, painted as a frame of two rectangles
      filled even-odd;
    - with those two entries removed, the same fill saves an appearance with
      no border at all.
  - The Viewer CI job checks the first case.
- **JavaScript actions: out.**
  - `PDFA-2B 6.5.1-1` forbids JavaScript actions in PDF/A, and `6.4.1-1` and
    `6.4.1-2` forbid `/A` and `/AA` on widgets and fields.
  - So they could never appear in the archival half of the release.
  - Client-side validation is a separate feature with its own surface.
- **Flattening: out.**
  - It converts fields to page content, which removes the widgets and with
    them the `Form` elements of section F. That needs its own decision about
    what the structure tree becomes.
  - Generated appearances as form XObjects make it cheap later: placing an
    appearance on the page is `place_form_xobject` of section B.

### Known limitation: PDFium substitutes its own font

**Observed in the stage 5b proof** (pypdfium2 5.14.0, PDFium 156.0.8076.0,
2026-10-23). The method: type into a field through PDFium's form-fill
environment (`FORM_ReplaceSelection`), save, and read the saved `/AP`.

- **Characters `/DR`'s font encodes** are drawn with the `/DR` font:
  - in a Helvetica field, `/Helv` with WinAnsi bytes;
  - in an embedded `Type0` field, the `/DR` `Type0` font with 2-byte codes.
- **Characters outside a standard-14 font's WinAnsi encoding**, such as Greek
  typed into a Helvetica field: PDFium adds a font of its own to the
  appearance's resources. It is a non-embedded `/TrueType` font (Arial on
  Windows) with `/Differences` at Windows-1253 codes, and is not added to
  `/DR`.
- **Greek typed into an embedded `Type0` field**, whose font has the glyphs
  and whose `/W`, `CIDToGIDMap` and `ToUnicode` cover them (section C): PDFium
  **still** adds its own non-embedded font, and does not use the `/DR` font.
- **The result depends on the host's fonts.** In a Linux container with no
  system fonts, PDFium wrote `/BaseFont /ChromeSansMM`, and the render
  dropped the Greek glyphs.
- **pdf.js** (pdfjs-dist 6.4.299), on a file without `/NeedAppearances`,
  regenerates the same Greek value with the `/DR` `Type0` font. With
  `/NeedAppearances true` it writes no `/AP` at all.

**What Tincture does about it.** Nothing in the file can make PDFium use the
`/DR` font for those characters. So the CI viewer check (section H) asserts
only what Tincture controls. Stage 5b states the limitation in the field
functions' `@doc` and in the README's form section. A file edited in PDFium
may also stop conforming to PDF/A, since the added font is not embedded;
section E's "What PDF/A covers" already says an edited file is outside the
claim.

### Known limitation: Acrobat Reader's dropdown list is WinAnsi

**Observed in Acrobat Reader 2026.002.22031** (2026-10-30), on a combo box in
the embedded Liberation Sans, with the options "Αθήνα", "Πάτρα" and "Βόλος"
and the value "Πάτρα":

- **At rest,** Tincture's appearance draws "Πάτρα" correctly.
- **With the list open,** Reader shows the options as "....a", "..t.a" and
  ".....": τ shows as t and α as a, and every other Greek letter as a dot.
- **A newly selected option** is drawn the same way until the document is
  saved.
- **After a selection and Save As,**
  - `/V` holds "Αθήνα", byte for byte one of `/Opt`;
  - `/Opt` is unchanged;
  - `/I [0]` is added;
  - Reader's saved `/AP` draws "Αθήνα" with `MyriadPro-Regular`, a CFF
    subset of its own, rather than the field's `/DR` font.
- **Reopened,** the field shows "Αθήνα" correctly at rest. Opening the list
  shows the options garbled again.

So in Acrobat Reader, a dropdown whose options use characters outside
WinAnsi shows its options garbled whenever the list is open, and a newly
selected option garbled until the document is saved. At rest after saving,
and in the stored value, the option is correct.

- The list is drawn by Reader. Nothing in the field's dictionaries is known
  to change it, so Tincture writes nothing different.
- `choice_field/7`'s `@doc` states the limitation.

### Tests

- **Per field type, single and multiline,** the appearance bytes are tested,
  including `/Q` quadding, auto size, wrapping and clipping.
- **The list-box selection** rectangle is tested.
- **The signature** gets an empty visible appearance test and a labelled one,
  and an invisible one, which has `/Rect [0 0 0 0]`, no `/AP`, and a `Form`
  element.
- **The list box's `/TI`:** absent when the selection is visible, and
  `min(k, len − n)` when it is not.
- **The `/Tx BMC … EMC` marking** brackets everything but the border, and no
  clip and no `q … Q` are written.
- **The measured values** above (sizes, baselines, padding, leading, list
  rows and band) are pinned against Acrobat's own numbers.
- **The password appearance** is exactly `/Tx BMC`, `EMC`, while its ruling
  is open.
- **No document writes `/NeedAppearances`.**
- **The push button's `/N`** is a stream.
- **The `/DA`/`/DR` consistency test** above.
- **WinAnsi appearance text:** a standard-14 field with value `"Größe"` writes
  `(Gr\366\337e)` or its hex equivalent in the appearance, not UTF-16.
- **The structure of `/AP`:** for every widget, `/AP` has only `/N`, a
  dictionary for a checkbox or radio button and a stream otherwise. This is
  a local mirror of `PDFA-2B 6.3.3-2` to `6.3.3-4`, except that a push
  button keeps a stream ("Checkbox, radio and push button").

### Fonts named only by `/DA` or `/DR`

**Decision (stage S, 2026-10-20), as amended by question 7, and by the
stage 7 plan (2026-11-02).** **In a document that declares PDF/A, a field
names a font only if it draws text with it.** Text and choice fields, and a
signature field with a `:label`, write `/DA`; a checkbox, a radio group and
a signature field without a label write none. No font that is not embedded
is ever named.

- **The rule.**
  - Each text or choice field's `/DA`, and each labelled signature's, names
    that field's own embedded font; the extended font check (below)
    refuses one that is not embedded.
  - `/DR` lists exactly those fonts, the fonts the appearances draw with,
    each the one object the appearances reference (section D). A document
    whose fields draw no text writes no `/DR`.
  - The AcroForm-level `/DA`, a document-wide default for variable-text fields
    (ISO 32000-1, Table 218), is not written. **This depends on one
    condition: every text and choice field writes its own `/DA`.** Table 222
    makes `/DA` required and inheritable for variable-text fields, and
    Table 218 makes the AcroForm-level value only the default a field would
    inherit. With every variable-text field carrying its own, nothing is left
    to inherit. The condition is tested (below).
  - A document whose only fields are checkboxes, radio groups and
    signatures without a label writes neither `/DA` nor `/DR`.
  - **A labelled signature keeps `/DA`, as a text field does.** This
    replaces stage S's "signature fields get no `/DA`". Its label's font must
    be embedded, by the extended check, so naming it names nothing a viewer
    could lack; and it keeps 5b's rule of one font, one alias, in `/DA`, in
    `/DR` and in the appearance. A signature field is not a variable-text
    field (Table 222), and no rule in the PDF/A-2 profiles tests `DA` or `DR`
    (stage 7 plan: a word search of every `<test>` in `PDFA-2B.xml` and
    `PDFA-2U.xml` finds none). Acrobat Reader and PDFgear drew a probe
    signature's label alike with and without `/DA` (Alex, 2026-11-02).
- **The case.** Checkboxes and radio buttons draw no text. In 0.3.4 their
  widgets still carry a `/DA`, and `/DR` lists that font: Helvetica by
  default, not embedded. It is accepted under PDF/A on the reasoning in
  `archival.ex:86-91` that the font never renders.
- **Why this is allowed.** ISO 32000-1:2008 places `/DA` with variable text.
  - Table 218, the interactive form dictionary: `DA` is "(Optional) A
    document-wide default value for the DA attribute of variable text
    fields", and `DR` is "(Optional)".
  - Table 222, "Additional entries common to all fields containing variable
    text", is where `DA` is "(Required; inheritable)".

  A button field contains no variable text, so it needs neither.
- **Evidence: observed.** Stage S question 7 built two PDF/A files without
  the library, each with no `/DA` and no `/DR` anywhere: one checkbox, and
  one two-button radio group.
  - Both pass veraPDF 1.30.2 at PDF/A-2b and, with `U` metadata, at
    PDF/A-2u.
  - No rule in either profile tests `DA`, `DR` or `AcroForm`.
- **Why it matters.** A viewer that regenerates an appearance draws with the
  `/DA` font. The spike's one saved file shows a viewer doing exactly that.
  A document that names an unembedded font there is one edit away from
  rendering with it.
- **A validator blind spot.** `PDFA-2B 6.2.11.4.1-1` is evaluated only on
  fonts used for rendering, the `PDFont` objects veraPDF reaches from a
  content-stream operator. A font named only by `/DA` and `/DR` is never
  reached, so veraPDF 1.30.2 passes a file whose only unembedded font is a
  checkbox's `/DR` Helvetica without checking that font at all.
- **Output change.** Archival documents with checkboxes or radio buttons lose
  `/DA` and `/DR` (section J, "Output changes"). Nothing they draw changes.

### Verified at byte level

The connection between a widget and its `Form` element is not a key veraPDF
reads as a whole: it is `/OBJR` one way, `/StructParent` and `/ParentTree` the
other. Stage 8a's acceptance therefore includes a written trace through
`tagged_form.pdf`, made from the file's bytes rather than from a parser in the
test suite. For each widget it records:

1. the `Form` structure element, by object number;
2. its `/K`, a single `/OBJR` whose `/Obj` is the widget;
3. the widget, and its `/StructParent` key;
4. the `/ParentTree` entry for that key;
5. that the entry is the same `Form` element as in step 1;
6. the `Form` element's `/P`, the element that was open at the field call.

A widget for which any step fails, or leads elsewhere, fails the stage.

### A `:form` structure element

- **Where.** `lib/tincture/pdf/structure.ex` gains `form: "Form"`.
- **Not a content element.** It must not join `@content_tags`
  (`structure.ex:60-84` at `af58aa2`), because it carries no marked content. 7.18.4-2
  requires that a `Form` without a Role attribute has exactly one child, the
  `/OBJR`, and an MCID would be a second.
- **Not a grouping element either.** It has no element kids.
- **A third kind: annotation-owning.** Its `/K` is the single `/OBJR`, written
  by the existing `/OBJR` path (`serialize.ex:737-744` at `af58aa2`).
- **No Role attribute.** Tincture never writes `/Role`, so 7.18.4-2's
  one-child condition always applies, and the design satisfies it by
  construction.
- **Inline-level.** `:form` joins the inline-level set (`@inline_level`,
  `structure.ex:103` at `af58aa2`, read by `Structure.inline_level?/1`). A `Form` element
  directly under a grouping element then gets `/Placement /Block` from the
  existing 0.3.4 mechanism (`serialize.ex:804-806` at `af58aa2`).
  - **Why.** In the spike, PAC 2026 gave *Possibly inappropriate use of a
    "Form" structure element* once for each `Form` element placed directly
    under `Document`. That was observed on the radio-group files, and
    inferred for the invisible-signature and `Div` files. It gave nothing for
    a `Form` element inside a `P`. This is the placement rule that flagged
    `Link` and `Figure` in the 0.3.4 audit, and the same remedy applies.
  - A `Form` element inside a content element such as `P` is inline already,
    and gets no `/Placement`.

### Who owns which widget

**Options.**

1. **The caller opens it.** The field function must be called inside
   `tag(pdf, :form, fn …)`, as a link is called inside a `:link`.
2. **Automatic.** In a tagged document, each field call creates one `Form`
   element per widget, as a child of the innermost open structure element.
3. **An explicit option** naming the parent element.

**Decision: option 2.**

- **Why.**
  - 7.18.4-2 fixes the shape completely: one widget, one `Form`, nothing else
    inside. So there is nothing for the caller to choose, and a scope they
    must open adds only the chance to open it wrongly.
  - Links associate automatically for the same reason, stated at
    `lib/tincture/pdf.ex:1315-1319` at `af58aa2`: "opt-in is the wrong default for a rule the
    format requires".
  - The difference from links is that a link's element is the caller's (they
    choose `:link`), whereas a `Form` element has no content of its own to
    scope.
- **The mechanism.** Field creation calls the same association path that
  `PDF.add_link/4` uses (`pdf.ex:1312`, `associate_annotation/2` at `1320-1325`, at `af58aa2`),
  except that it appends a new `:form` child, which owns the widget's id, to
  the innermost open element. It does not attach the id to that element
  directly.
- **With no open element** in a tagged document, the widget is outside the
  structure. Export refuses it as a new violation, `:field_outside_structure`
  (clause 7.18.4), mirroring `:link_outside_structure`
  (`lib/tincture/pdf/accessibility.ex:149-150` at `af58aa2`). In an untagged document,
  nothing is created and nothing is checked, as for links. This is breaking,
  with a 0.3.6 deprecation first (section J, item J2).

**The innermost open element as a content element.** **Decision (stage S, 2026-10-20).**
**Allowed.** The `Form` element is appended to the innermost open element,
whatever its kind, including a content element such as `:p`, whose `/K`
already holds MCIDs. The `Form` element is then a sibling of marked content
inside a `P`.

- **Evidence: observed.** veraPDF 1.30.2 passes PDF/UA-1 in full both for a
  `Form` element inside a `P` with MCID kids, and for one under a `Div`. PAC
  2026 reports 0 warnings for the `P` case. It reports one warning for the
  `Div` case, inferred to be the placement warning that `/Placement /Block`
  removes (above).
- **No refusal and no deprecation.** The refusal considered here is not
  built, and 0.3.6 carries no warning for it.

**The radio group** is one field with N widgets (`serialize.ex:1333-1362` at `af58aa2`).

- It gets **N `Form` elements, one per button widget**, all children of the
  element that was open when `radio_group/4` was called, in button order. Each
  owns its kid widget.
- One `Form` with N `/OBJR` kids would break 7.18.4-2 without a Role
  attribute.
- Buttons on different pages are allowed (`:page` per button,
  `lib/tincture.ex:602` at `af58aa2`). Each `Form` element records its widget's page.

**Signature fields** get one `Form` element like any other widget, visible
and invisible alike (section D).

**`/StructParent`** is written on every owned widget. Its key is taken from
the same counter as link annotations (`serialize.ex:1256-1263` at `af58aa2`), and
`/ParentTree` maps it to the `Form` element (`parent_tree_body/4`,
`serialize.ex:686-721` at `af58aa2`). That is the existing mechanism, applied to widgets.
The only new part is the ownership described above.

- **The key ranges.** Pages take `0..n-1` (`/StructParents`), the links
  `n..n+k-1`, as before, and the widgets the keys after, in field order. So a
  tagged document without fields keeps every key and every byte. Measured on a
  two-page probe with a link and four widgets: pages 0 and 1, the link 2, the
  widgets 3 to 6, `/ParentTreeNextKey 7`.
- **Widget numbers are known before the widgets are written.** A field's
  objects are numbered from its type alone, so the structure tree can name a
  widget by `/OBJR` before the field objects are built; export checks each
  number it used against the widgets written.
- **Built in stage 8a-1**, with `tag/4` refusing `:form`: each field call
  creates its own `Form` elements, and one opened by the caller would have no
  widget to own.

### `/TU` is required in tagged documents

`:tooltip` is already written as `/TU` (`tooltip_entry/1`, `serialize.ex:1686-1689` at `af58aa2`).

**Decision**, confirmed 2026-10-20. In a tagged document, every field must have a
non-blank `:tooltip`. Export refuses one without it, as a new violation:

```
rule: :field_without_description, clause: "7.18.1"
message: a text field "full_name" on page 1 has no tooltip. In a tagged
document every form field needs one: it is written as /TU, the name a screen
reader announces for the field. Pass tooltip: "..."
```

- **Only in tagged documents.** Requiring `:tooltip` on untagged fields is
  out: an untagged document makes no accessibility claim.
- **Breaking,** with a 0.3.6 deprecation first (section J, item J1).
- **Why export time.** This is the same reason that `:contents` on links is
  required only in a tagged document (`accessibility.ex:124`,
  `link_structure_test.exs:207`): whether a document is tagged is known only
  once tagging has happened.
- **Why `/TU` rather than `Alt`.** 7.18.1-3 also accepts an `Alt` on the
  enclosing structure element. Requiring `/TU` gives one rule rather than
  two, and `/TU` is also what a non-assistive viewer shows on hover.
- **Language.** 7.2-25 is met by the catalog `/Lang` from `set_language/2`.
  - *Established in the stage 8a plan:* a tagged document without
    `set_language/2` was not refused, and every tagged document claims
    PDF/UA-1 (`pdfuaid:part` in its XMP). veraPDF fails one with text on
    7.2-34 ("Natural language for text in page content shall be determined"),
    one with a field's `/TU` on 7.2-25, and one with a title on 7.2-33.
  - *Decision (2026-11-05), built in stage 8a-1:* export refuses a tagged
    document with no language, as `:language_missing`, clause 7.2, naming
    7.2-34, 7.2-25 and 7.2-33, under `:enforce`. No warning release first:
    the file would claim a conformance it does not have. The CHANGELOG's
    Breaking section records it.
  - *Decision (2026-11-05, at review), built in stage 8a-1:* an element's
    `:lang` does not satisfy the refusal. A tagged document needs
    `set_language/2`; `:lang` refines it for one element. `set_language/2`
    and `tag/4`'s `:lang` say so, and the refusal message names
    `set_language/2`.
- **Title.** *Decision (2026-11-05, at review), built in stage 8a-1:* a
  tagged document with no title is refused, as `:title_missing`, clause
  7.1, naming 7.1-9 ("The Metadata stream in the document's catalog
  dictionary shall contain a dc:title entry"), under `:enforce`, with no
  warning release first, for the same reason as the language. A blank title
  counts as none. Measured: a tagged document with a language and no title
  fails 7.1-9 and nothing else.

**The radio group.** **Decision (stage S, 2026-10-20).** **`/TU` on the parent field only.**
The group takes one `:tooltip`, written as `/TU` on the parent field. No
`/Alt` is written on each kid's `Form` element.

- **Evidence: observed.** veraPDF 1.30.2 resolves `TU` from each kid
  widget's parent field: 7.18.1-3 passes for all three kid widgets with `/TU`
  on the parent alone. Adding `/Alt` on each `Form` element changes nothing
  for veraPDF or for PAC. PAC's 3 warnings are identical with and without
  `/Alt`, and each reads *Possibly inappropriate use of a "Form" structure
  element*: placement, not `/TU`.

The caller's API is one `:tooltip` on `radio_group/4`.

### Identical structure elements

**Found in the stage 8a plan, fixed in stage 8a-1.** Structure objects were
numbered by looking each element up by value, so two elements equal as terms
got one object: two empty `:section` scopes on one page, or two sections each
holding only a field, wrote `/K [13 0 R 13 0 R]`, and the other element was
unreachable. No veraPDF rule reported it. Elements are now numbered by their
position in the tree, for every element kind; parents, kids, the parent tree
and the ID tree follow that numbering. `Form` elements would have been
distinct anyway, by the widget each owns.

### `/Tabs /S`

**Fact.** It is written on **every page of a tagged document**, whether the
page has annotations or not (`serialize.ex:179-186` at `af58aa2`,
`tabs = if PDF.tagged?(pdf), do: " /Tabs /S", else: ""`). So pages with links
in a tagged document carry it today, and 7.18.3-1 holds for them.

**Decision for widgets: unchanged.**

- A tagged document with widgets has `/Tabs /S` on every page, so 7.18.3-1
  holds.
- An untagged document claims no PDF/UA, and keeps writing no `/Tabs`, so its
  bytes do not move.

- **Parsing tests** in the style of `test/tincture/link_structure_test.exs`

### Stage S — the spike

Hand-written PDF files, built without the Tincture API, by a small script.
None of them enters `examples/`. Each file is validated with veraPDF 1.30.2,
the version CI runs. The outcome of each question is recorded before any
stage that depends on it, and selects the decisions marked **pending spike**.

**The evidence is kept.** The spike's files, the script that generated them

### Stages 1–9

**Branches.** `design-0.4.0` is the integration branch.

- `main` stays equal to the latest release until 0.4.0 ships. A 0.3.x fix,
  if one is needed, goes on `main` as before, and `main` is then merged into
  `design-0.4.0`.
- Each stage branches from `design-0.4.0` and merges back after review.
- At release, `main` is fast-forwarded to `design-0.4.0`, and `design-0.4.0`
  is deleted.

Only three kinds of commit land on `design-0.4.0`:

1. merges of `main`;
2. merges of reviewed branches, with `--no-ff`: **stage branches**, and
   **maintenance branches** (`maint-<topic>`) that change no file under
   `lib/` and no output byte (tests, CI, tooling and docs only);
3. design-doc commits that touch only `docs/design/`. They are never mixed
   into a stage commit.

Each stage is reviewed and merged on its own. Each ends with:

- `mix check` green;
- CI green on its branch;
- every committed example byte-compared against `main`, with every
  difference explained;
- **the compatibility gate**: the previous release's `test/` tree is run
  against the stage's base and against its branch. The two failure sets must
  be identical, unless the stage intends a difference and names each one;
- **docs follow behaviour**: a stage that changes behaviour searches README,
  ROADMAP, `examples/README.md` and the `@doc` of every function it touches
  for passages describing that behaviour, lists every hit, and corrects
  those that are now false before it merges;
- a stop point for review before merge.

Stages 5 and 8 are split, and stage 1b follows stage 1, so stages 1–9 are
twelve stages; stage 1c, added with 0.3.8, makes thirteen.

**Between 5a and 5b (decision, 2026-10-21).** Two released defects concern
how Tincture ends a path: `paint: :none` writes `n`, which ends the path its
documentation says a later `fill/1` or `clip/1` paints; and an image or
gradient drawn while a path is open writes `q … Q` inside a path object. They
are decided together, as one rule, and shipped in 0.3.8 before stage 5b. The
order is: 5a merged; `maint-doc-claims`; a path-state plan (facts, the
standard's operator-order rules quoted, and proposals, with no code); 0.3.8
from `main`, then `main` merged into `design-0.4.0`; 0.3.9 (W7, decided
2026-10-22) from `main`, merged the same way; then stage 1c, which turns 0.3.8's
and 0.3.9's warnings into refusals; then 5b. The rows below record it, and
section A ("Path state") holds the rule.

**Between 1c and 5b (decision, 2026-10-23).** The stage 5b plan found four
defects in released form code:

- the AcroForm `/DA` naming a font `/DR` lacks;
- the push-button caption written as UTF-16 under a WinAnsi font;
- `sort: true` sorting nothing;
- a non-editable choice field accepting a value outside its options.

They ship in **0.3.10**, from `main`, before 5b, because 5b rewrites the same
code. `main` is then merged into `design-0.4.0`, and 5b builds on the fixed
version.

**Why the deprecations come first:**

- They are independent of everything else and are the smallest stage.
- Stage 2 rewrites the functions that W1 and W2 live in (`paint_open_path/4`
  reads the current page's operations; `warn_open_marked_content/2` reads
  them on page change). Making them errors first means stage 2 generalises
  the final code, not a warning path that is about to change.
- Last would also work, but it would leave a breaking change to land on top
  of the largest refactor in the release, where a regression is hardest to
  attribute.

**Why stage 2 is separate from stage 3.** Stage 2 is pure plumbing, and is
proved by byte-identity alone. Folding it into the font work would mean one
diff in which a byte change could come from either.

**Why 5a before 5b.** The font decisions are the ones the spike settles, and

**Why stage 5b has a visual review.** Removing `/NeedAppearances` changes how

- **Every example but `form.pdf`** is byte-identical, which implies pixel

## J. Changes that are not backward compatible

J3 was withdrawn after stage S (question 5); the numbers of the others are
unchanged.

Every behaviour in 0.4.0 that makes code working on 0.3.4 fail, or changes
its output. Each is classified as:

- **breaking:** the call or the export now raises;
- **output change:** the call still works, but the bytes differ;
- **new API only:** nothing existing is affected.

Every breaking item has a deprecation in 0.3.6, with these exceptions:

- W1–W4 warned in 0.3.4;
- W5 and W6 warn in 0.3.8, and W7 in 0.3.9 (J5);
- W8 warns in 0.3.10;
- W9 warns in 0.3.13.

- is raised with `IO.warn/1`, as the 0.3.4 warnings are (for example
  `lib/tincture/pdf.ex:273-278`);

An export-time refusal in 0.4.0 follows `enforce:` like every accessibility
refusal (`lib/tincture.ex:1697-1720`): with `enforce: false` it is logged

**An embedded font without a readable character map (stage 1e).**
`register_ttf_font/3,4` and `register_otf_font/3,4` raise `ArgumentError`
for a font with no cmap data the library reads, and for an `OTTO` file whose
tables do not parse. There is no warning release first.

- **Why.** Such a font draws every character wrong. With no cmap, glyphs are
  chosen as glyph = character code, and widths with them: Latin text in a
  simple TrueType font has the right letters at the wrong spacing, `Type0`
  text has the wrong glyphs, and text extraction, which reads a correct
  `ToUnicode`, disagrees with what is shown. veraPDF reports the simple-font
  case (ISO 19005-2 6.2.11.5 test 1 and 6.2.11.6 test 1; ISO 14289-1 7.21.5
  test 1 and 7.21.6 test 1), and nothing in the `Type0` case, where the
  widths agree with the wrong glyphs. The veraPDF results and the renders,
  the renders in PDFium only, are from a probe of Liberation Sans with its
  `cmap` table renamed, on `design-0.4.0` at `6e9e65b`. It was so in every
  release, `v0.1.0` through `v0.3.13`.
- **Condition.** At registration, in `PDF.register_embedded_font/6`, before
  anything is added or any embedding-permission warning is given: the
  parsed `cmap_by_code` is empty (shape A), or an `OTTO` file's tables do not
  parse (shape B). Shape A has four causes the parser tells apart, and the
  message names the one found: no `cmap` table; a table header that does not
  parse; no subtable in a format the parser reads (0, 2, 4, 6, 8, 10, 12 or
  13), as for a font whose only subtable is format 14; a subtable that maps
  nothing. A `cmap` table that lies outside the file is not among them: the
  table directory refuses it first, and the TrueType path raises "invalid
  TTF file".
- **Messages.** Shape A: `font file "…" has no character map (cmap) that
  Tincture can read, so no character could be drawn with its glyphs: it has
  no cmap table. Use a TrueType or OpenType font with a Unicode cmap
  subtable (format 4 or 12).`, with the cause after the colon. Shape B:
  `font file "…" is not a readable OpenType font: its tables could not be
  parsed.`
- **No warning release first.** This is a deliberate, recorded exception to
  the rule that nothing breaks without a warning: the rule protects output
  that is correct, and none was measured. Every probed case draws wrong
  (wrong spacing for ASCII, wrong glyphs for `Type0`, which no validator
  catches), no committed example uses such a font, and 0.3.x releases have
  stopped except for data-corrupting defects.
- **What becomes unreachable, and is removed.** The fallback chain's OS/2
  branch and its `codepoint <= 255` clause, with its code page tables;
  `Tincture.Font.UnicodeRanges` is public, and stays. The `/Identity`
  `CIDToGIDMap` for an empty cmap. The subset skip for an empty cmap.
- **What stays.** `glyph_id_for_char_code/2`'s default of glyph = code,
  which also serves fonts with a cmap. The combining-mark zero-width
  handling, now reached only by standard-14 fonts. `Context`'s measurement
  of a code point a font's cmap lacks, glyph = code up to 255 and glyph 0
  above: it is not specific to fonts without a cmap, and the public
  `Tincture.Font.Context.text_width/5` reaches it for fonts with one.
- **Test.** A refusal test for each cause and for shape B, each with its full
  message; one showing that the refusal comes before the embedding-permission
  warning; two showing that OS/2 Unicode or code page ranges do not rescue a
  font without a cmap. The fixtures of the tests that registered a font
  without a cmap get one, their assertions unchanged.
