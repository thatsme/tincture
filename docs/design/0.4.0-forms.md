# 0.4.0 — forms, completed

Status: **proposed.** Nothing described here is implemented. Facts about the
current code are given as `file:line` at `2bed2f9`; line numbers describe that
commit and will drift once implementation starts.

0.4.0 contains two things:

- the four behaviours deprecated in 0.3.4 become errors;
- interactive forms become usable in archival and accessible documents.

For forms, that means three changes. Every field gets a generated
appearance, so `/NeedAppearances` is never written. Fields can use embedded
fonts. And every widget is owned by a `Form` structure element.

Getting there needs two general mechanisms, which the rest of the release
builds on: form XObjects as a public primitive, and a font pipeline that
serves any content stream rather than only pages.

## Sources and how they are cited

- **veraPDF rules** are cited as `<profile> <clause>-<test>`, for example
  `PDFUA-1 7.18.4-1`. They are taken from the profile XML shipped in
  veraPDF 1.30.2 (`cli-1.30.2.jar`, `org/verapdf/pdfa/validation/PDFUA-1.xml`,
  `PDFA-2B.xml`, `PDFA-2U.xml`, `PDFA-2A.xml`), the same version CI runs. The
  rule texts quoted below are the profile's own `<description>` and `<test>`.
- **ISO 32000-1 clause numbers** are cited only where a veraPDF rule
  description names them. Any other clause number is marked **unverified**.
- **PAC checkpoints** are not cited anywhere. PAC has no command line and its
  checkpoint list was not consulted for this document, so every statement
  about PAC is **unverified**.
- **Viewer behaviour** (what Acrobat, Preview or pdf.js do with a field) is
  **unverified** throughout. Decisions do not rest on it. Where it matters, it
  is listed as a risk.

A claim marked **unverified** is never the reason for a decision.

## A. The four deprecations become errors

### Current behaviour

The four warnings, as of 0.3.4:

| | Site | Raised when |
|---|---|---|
| W1 | `lib/tincture/pdf/ops.ex:144`, `paint_open_path/4` | `stroke/1`, `fill/1`, `fill_even_odd/1`, `clip/1`, `clip_even_odd/1` with no open path |
| W2 | `lib/tincture/pdf.ex:273`, `warn_open_marked_content/2`, from `add_page` (`pdf.ex:231`) and `set_page` (`pdf.ex:249`) | a page change while a content tag or artifact is open |
| W3 | `lib/tincture/pdf.ex:532`, `resolve_figure_bbox/2`, run by `end_structure/1` (`pdf.ex:375`) | a `:figure` that draws nothing and has no `:bbox` is closed |
| W4 | `lib/tincture/pdf.ex:600`, `warn_ignored_bbox/1`, run by `structure_options/3` (`pdf.ex:339`) | `tag/4` opens an element with an unusable `:bbox` |

All four are detected **at call time**. Each has complete information at the
moment of the call.

### Options

1. Raise at call time, where the condition is detected.
2. Record the condition and raise from `export/2`, alongside the PDF/A and
   PDF/UA refusals (`lib/tincture.ex:1670-1720`).

### Decision: raise `ArgumentError` at call time

- **Exception.** It is `ArgumentError`, which is what every existing refusal
  raises: the export-time refusals in `check_archival/2` and
  `check_accessibility/2` (`lib/tincture.ex:1688`, `1712`), and the call-time
  ones such as `normalize_field_font/1` (`lib/tincture/pdf.ex:1311`) and the
  unknown-page check (`pdf.ex:1110`).
- **Moment.** Call time.
  - The stack trace then points at the caller's line, which is the line to
    change.
  - The export-time refusals collect findings from the whole document. These
    four conditions concern a single call.
- **No `enforce: false` escape.** `enforce:` exists so that a document can be
  iterated on while its conformance claim is not yet true
  (`lib/tincture.ex:1649-1651`). None of these four describes a document that
  is merely non-conforming. W1 and W2 produce invalid content streams. W3 and
  W4 are arguments that cannot be honoured.

### Messages

Each says what to do instead.

- **W1:** `Tincture.stroke/1 was called with no open path, so there is nothing to paint. A shape paints itself: pass its own paint argument (for example rectangle(pdf, x, y, w, h, :stroke)) instead, or start a path with move_to/3.`
  The function name and the paint example vary as today
  (`ops.ex:145-149`).
- **W2:** `Tincture.add_page/1 was called while tag(:p, ...) is open on page 1. Its marked content would begin on one page and end on another, which a content stream cannot hold. Close it before changing page.`
  `set_page/2` and the artifact wording vary as today (`pdf.ex:274-277`).
- **W3:** `Tincture.tag(:figure, ...) with alt text "…" on page 1 draws nothing, so it has no bounding box. Draw its content inside the tag, or pass bbox: {left, bottom, right, top}.`
- **W4:** `Tincture.tag/4: <problem>. Pass bbox: {left, bottom, right, top}, four numbers within the page with left < right and bottom < top, and only on :figure.`
  The `<problem>` strings are unchanged (`pdf.ex:580-587`, `571`).

One behaviour is unchanged. A figure closed on a different page from the one
it opened on gets no `/BBox` and no error (`pdf.ex:516-520`, `:spans_pages`).
The design does not depend on that being a requirement of ISO 32000-1
(Table 344 is **unverified** here); it only keeps the 0.3.4 behaviour.

### Bytes

None change. Since 0.3.4, a document that triggers W1–W4 already writes no
operator, or writes the computed box (CHANGELOG 0.3.4). A document that does
not trigger them is unaffected.

### Documentation

- The `@doc` of `add_page/1` and `set_page/2` gains a paragraph: changing page
  while a content tag or an `artifact/2` block is open raises, because marked
  content cannot span content streams.
- The five painting functions' `@doc` lines (`lib/tincture.ex:1054`, `1069`,
  `1084`, `1099`, `1114`) change from "0.4.0 will raise rather than warn" to
  "raises".
- `tag/4`'s `:bbox` and figure paragraphs (`lib/tincture.ex:1427`, `1447`)
  change the same way.

CHANGELOG, under `### Breaking`:

- **`stroke/1`, `fill/1`, `fill_even_odd/1`, `clip/1` and `clip_even_odd/1`
  raise with no open path.** *Migration:* pass the shape's own paint argument,
  `rectangle(pdf, x, y, w, h, :fill)` in place of
  `rectangle(pdf, x, y, w, h) |> fill()`, or open a path with `move_to/3`.
- **`add_page/1` and `set_page/2` raise while a content tag or an `artifact/2`
  block is open.** *Migration:* close the tag before changing page, and open
  a new one on the next page.
- **A `:figure` that draws nothing raises when it closes.** *Migration:* draw
  the figure's content inside the tag, or pass `bbox:`.
- **An unusable `:bbox` raises.** *Migration:* pass four numbers within the
  page, ordered, and only on `:figure`; or omit it and let the box be
  computed.

Every one of these warned in 0.3.4, so a caller with no warnings in 0.3.4 is
unaffected.

### Tests

- The warning tests become `assert_raise ArgumentError, ~r/…/`:
  - `test/tincture/open_path_test.exs:29` and `:60`;
  - `test/tincture/marked_content_pages_test.exs:17`, `:33`, `:46`, `:55`;
  - `test/tincture/layout_attributes_test.exs:221`, `:233`, `:279`, `:289`.
- The "does not warn" tests stay as they are, asserting no exception:
  `open_path_test.exs:44`, `marked_content_pages_test.exs:68` and `:75`,
  `layout_attributes_test.exs:240`.
- A grep test asserts that `lib/` no longer contains `"This will raise in 0.4.0"`.

## B. Form XObjects as a public primitive

### Current behaviour

- **One private writer.** `form_xobject/4` (`lib/tincture/pdf/serialize.ex:1384-1391`)
  takes width, height, a content string and a resource string. It writes
  `/BBox [0 0 w h]` and no `/Matrix`.
- **Three callers.** It is used only by the checkbox, radio and push-button
  appearance builders (`serialize.ex:1286-1360`). Each assembles its content
  as a string, not from drawing operations.
- **Resources by hand.** The only font it carries is the push-button
  caption's inline `/Helv` Type1 dictionary (`serialize.ex:1374-1376`).
- **No `/XObject` resources but images.** Page XObject resources list images
  only (`xobject_resources/2`, `serialize.ex:971`).
- **Operations live on pages.** Every drawing function appends to
  `pdf.pages[pdf.current_page]`, through `append_current_op`. They are read
  back with `PDF.page_operations/2` (`lib/tincture/pdf.ex:223-226`).

### Options for the API

1. **A builder over a separate document value.** It is drawn into and then
   attached. This is rejected: fonts, images and alpha states are registered
   on the document, so they would have to be merged back afterwards.
2. **Redirect the existing drawing functions inside a callback**, the way
   `tag/4` scopes structure. The callback receives the document, and every
   drawing call inside it appends to the XObject's operations instead of the
   page's.
3. **Explicit operation lists** passed to a constructor. This is rejected: it
   would make the drawing API a second time, as data.

### Decision: option 2

The new public API:

```elixir
pdf
|> Tincture.form_xobject(:stamp, 200, 40, fn pdf ->
  pdf
  |> Tincture.set_font("Body", 10)
  |> Tincture.text_at(4, 14, "APPROVED")
  |> Tincture.rectangle(0.5, 0.5, 199, 39, :stroke)
end)
|> Tincture.place_form_xobject(:stamp, 72, 600)
|> Tincture.place_form_xobject(:stamp, 72, 300, scale: 0.5)
```

`form_xobject(pdf, name, width, height, fun)`:

- **The name** is an atom or a string, and must be unique: a second
  definition raises `ArgumentError`.
- **The coordinate space** is `[0 0 width height]`, with its origin at the
  bottom left, as on a page.
- **The callback** is run with the document's drawing target set to the
  XObject. Inside it, every drawing, text, colour, state and image function
  works unchanged.
- **Refused inside the callback**, with `ArgumentError`:
  - `add_page/1` and `set_page/2`;
  - `tag/4` and `artifact/2`;
  - `link/7` and `text_link/6`;
  - every form-field function;
  - a nested `form_xobject/5`.

  Annotations and structure elements belong to pages, not to content streams.
  A nested definition adds a case nothing in 0.4.0 needs.

`place_form_xobject(pdf, name, x, y, opts)`:

- Draws the XObject on the current page, with its origin at `(x, y)`.
- **Options:**
  - `:scale`, a number that defaults to 1;
  - `:width` and `:height`, which scale to fit and override `:scale`.

  Rotation is out of scope (section I).
- **An unknown name raises.**
- **In a tagged document** the placement is content, like any other drawing
  operation. It must sit inside a content tag or an `artifact/2` block, and
  the `Do` falls inside that tag's marked content.
- **In a `:figure`**, the figure's computed `/BBox` includes the XObject's
  `/BBox` transformed by the placement matrix. That is a change to
  `lib/tincture/pdf/figure_bounds.ex`, which today knows nothing of `Do`.

### Internal model

- **Content streams instead of pages.** The document's operations move from
  `pages` (a page number → operations map) to content streams, keyed
  `{:page, n}` or `{:xobject, name}`.
- **One accessor.** `PDF.page_operations/2` becomes a special case of
  `PDF.stream_operations(pdf, key)`.
- **One write path.** `append_current_op` appends to the stream named by a
  new `current_stream` field, which is `{:page, pdf.current_page}` outside a
  callback.
- **Appearance streams are content streams too**, keyed
  `{:appearance, field_name, widget_index, state}`. They are generated at
  serialisation time from field data (section D), but they go through the same
  font discovery and resource naming as everything else (section C).

### `/BBox`, `/Matrix` and resources

- **`/BBox`** is `[0 0 width height]`, given by the caller.
- **`/Matrix`** is omitted. The default is the identity (ISO 32000-1 8.10.2,
  **unverified**). Placement is expressed in the page's content stream
  instead: `q a 0 0 d x y cm /FmN Do Q`. That keeps the XObject reusable at
  different positions and scales, with one object.
- **Resources** are collected per stream, by the same functions that collect
  them for pages:
  - `font_resources/2` (`serialize.ex:945`);
  - `xobject_resources/2` (`:971`);
  - `ext_gstate_resources/1`;
  - `shading_resources/1`.

  They are generalised from a page's operations to any stream's (section C).
  Resource names are local to each stream, as `/F1…` already are per page.
- **The page's own `/XObject` resources** gain `/FmN` entries next to the
  images' `/ImN` entries.
- **Each form XObject is one indirect object**, however many times it is
  placed.

### Bytes

```
12 0 obj
<< /Type /XObject /Subtype /Form /BBox [0 0 200 40] /Resources << /Font << /F1 9 0 R >> >> /Length 61 >>
stream
BT
/F1 10 Tf
4 14 Td
(APPROVED) Tj
ET
0.5 0.5 199 39 re
S
endstream
endobj
```

On the page, its resources gain `/XObject << /Fm1 12 0 R >>`, and its
content stream gains:

```
q
1 0 0 1 72 600 cm
/Fm1 Do
Q
q
0.5 0 0 0.5 72 300 cm
/Fm1 Do
Q
```

With an embedded font, the `Tj` operand is the font's encoded string, exactly
as on a page.

### How `form_xobject/4` is replaced

- The private `form_xobject/4` becomes the one writer for every form XObject,
  public or generated.
- Its signature changes from `(width, height, content_string, resource_string)`
  to `(bbox, stream_key)`. The content and resources are produced by the
  shared stream serialiser, not passed in as strings.
- The three button builders stop assembling strings. They produce operation
  lists into appearance streams (section D).

### What it must not preclude

Patterns (ROADMAP item 5) need a tiling pattern's cell. Soft masks on drawn
content (ROADMAP item 6) need a transparency group form XObject as the
mask's `/G`. Both are content streams with their own resources, which is
exactly what `{:xobject, name}` streams are. Two things are kept open:

- the stream key space is open, so a later `{:pattern, name}` or `{:group, name}`
  is an addition rather than a change;
- `form_xobject/4` writes the dictionary from a map of entries, so `/Group`
  (needed for soft masks; ISO 32000-1 11.6.5, **unverified**) can be added
  without restructuring.

Neither patterns nor soft masks are built in 0.4.0.

### Tests and claims

- **Unit tests:**
  - the XObject object and the placement bytes above;
  - one object for two placements;
  - per-stream resource naming;
  - refusals inside the callback;
  - an unknown name;
  - a duplicate definition.
- **Figures:** a `:figure` containing a placement gets a `/BBox` that
  includes the transformed XObject `/BBox`.
- **Validation:** `PDFUA-1 7.20-2` ("The content of Form XObjects shall be
  incorporated into structure elements", test `isUniqueSemanticParent == true`)
  must run.
  - The tagged form example (section G) places one XObject twice, inside two
    different content elements.
  - **If veraPDF reports 7.20-2 for that**, placing one XObject under two
    different structure elements is refused in a tagged document, and the
    example changes to one placement.

  This is decided by the validator run, not here.

## C. The font pipeline beyond pages

### Current behaviour

Font handling is coupled to pages in three places:

1. **Discovery.** `FontEmbed.build_embedded_font_objects/3`
   (`lib/tincture/pdf/font_embed.ex:32-48`) walks `page_numbers` and
   `PDF.page_operations/2`. `font_names_from_operations/1` (`:107-115`)
   recognises only `{:text_at, …}` and `{:text_at_rotated, …}`.
2. **Subsetting.** `used_char_codes_by_font/2` (`:117` ff.) and the other
   `*_by_font` collectors (`:33-38`) walk the same page operations.
3. **Resource naming.** `font_resources/2` (`lib/tincture/pdf/serialize.ex:945-967`)
   names `/F1…/Fn` per page.

Two more facts bound the design:

- **Fields refuse embedded fonts.** `normalize_field_font/1`
  (`lib/tincture/pdf.ex:1307-1316`) raises for anything but the standard 14.
- **`/DR` is standard 14 only.** `acro_form_font_resources/1`
  (`serialize.ex:769-777`) writes inline standard-14 Type1 dictionaries.

### Decision: discovery and subsetting over every content stream

- **The input changes.** `build_embedded_font_objects/3` takes the list of
  content streams to be written, instead of `page_numbers`: pages,
  `{:xobject, _}` and `{:appearance, …}`. Every `*_by_font` collector walks
  the same list.
- **One subset per font for the whole document**, as today: one font object,
  one `FontFile2`/`FontFile3`, referenced from every stream that uses it.
- **Appearance streams are built first.** They are generated as operation
  lists before font embedding runs. The serialiser's order becomes:
  1. build appearance operation lists;
  2. collect the streams;
  3. embed fonts;
  4. allocate objects;
  5. write.
- **`font_resources/2` takes a stream's operations**, not a page's. Its
  output format does not change.

### Acceptance

1. **A glyph used only in an appearance stream is in the subset.** The test is
   a document whose page text never uses `Q`, with a text field whose value is
   `"Q"`. The font's subset must contain the glyph, checked by parsing the
   embedded `glyf`/`loca` (or `CFF `) and the font's `/Widths`.
   - The veraPDF evidence is `PDFA-2B 6.2.11.4.1-2` ("Embedded fonts shall
     define all glyphs referenced for rendering within the conforming file").
   - It runs on the archival form example (section G).
2. **Output with pages only stays byte-identical.** Every committed example in
   `examples/output/`, other than `form.pdf`, is byte-compared against `main`
   at the end of each stage that touches the pipeline. `form.pdf` changes by
   design (section D).
3. **The `*_by_font` collectors** are tested against a synthetic stream list
   that mixes pages and an XObject.

### Decision: fields may use embedded fonts

`normalize_field_font/1` accepts any font registered with
`register_ttf_font/4` or `register_otf_font/4`, as well as the standard 14.

### Character codes in field values and `/DA`

**The problem.**

- A field's appearance is generated by Tincture from its value, so the value's
  glyphs are in the subset (acceptance 1).
- A viewer that lets someone edit the field regenerates the appearance from
  `/DA` and the font in `/DR`, with whatever characters were typed. It can only
  draw glyphs the embedded font program contains.
- How a given viewer behaves when a glyph is missing, and whether viewers
  regenerate appearances with a `Type0`/`Identity-H` font from `/DR` at all,
  is **unverified**.

**Options.**

1. **Embed the whole font** for any font used by an editable field. The cost
   is size (a full TrueType program, often hundreds of kB), and the font's
   embedding permissions must allow it, which `register_ttf_font/4` already
   inspects (`:enforce_embedding_permissions`, `lib/tincture.ex:657`).
2. **Subset, plus a documented limitation**: an edited value can only use
   glyphs that were in the subset.
3. **Refuse** an embedded font on an editable field. Editable fields keep the
   standard 14, and so remain impossible in PDF/A (`PDFA-2B 6.2.11.4.1-1`,
   section E).

**Decision: option 1, for editable fields only.**

- **When a font is embedded whole.** A font used by the `/DA` of any field
  that is not `read_only:` is embedded without subsetting, for the whole
  document. It is still one font object.
- **Read-only fields** are subset like any other text: their appearance is
  final, since no viewer edits a read-only field.
- **Why not option 2.** It ships a form whose ordinary use produces broken
  output, and the failure appears only in the hands of the person filling the
  form.
- **Why not option 3.** It forfeits archival editable forms, which is the
  point of the release.
- **The size cost** is stated in the `@doc` of `text_field/7` and
  `choice_field/7`.

**The `/DA` font is a simple font.**

- **The dictionary.** The font is referenced from `/DR` as a simple TrueType
  font dictionary, `/Subtype /TrueType /Encoding /WinAnsiEncoding`, sharing
  the same `FontFile2` stream as any other dictionary for that font.
- **Why.** A single-byte encoding is the one that `/DA`-driven regeneration
  can be expected to handle. That expectation is **unverified**, and it is
  listed as an open question at the end of this document.
- **Two dictionaries are allowed.** `PDFA-2B 6.2.11.6-2` allows a non-symbolic
  TrueType font with `WinAnsiEncoding`.
- **The consequence.** An editable field's value, and its options for a choice
  field, must be WinAnsi-encodable. Anything else raises `ArgumentError` at
  call time, naming the character.
- **Read-only fields** use the same dictionary the document's page text uses,
  so Type0 Unicode text works.
- **CFF fonts.** An editable field with an OpenType/CFF font raises in 0.4.0.
  A simple CFF font needs `FontFile3 /Type1C` with a Type1 dictionary, and
  that path is not built here.

### Bytes

The `/DR` of a form whose editable fields use an embedded TTF font registered
as `"Body"`:

```
/AcroForm << /Fields [20 0 R 23 0 R] /DA (/Body 0 Tf 0 g) /DR << /Font << /Body 31 0 R >> >> >>

31 0 obj
<< /Type /Font /Subtype /TrueType /BaseFont /Body-Regular /FirstChar 32 /LastChar 255 /Widths 32 0 R /FontDescriptor 33 0 R /Encoding /WinAnsiEncoding >>
endobj
```

- `33 0 R` carries `/FontFile2` pointing at the whole program.
- With a full embed, the `/BaseFont` has no subset tag. With a subset it has
  one (`ABCDEF+`), as today.
- The `/FirstChar 32 /LastChar 255` range for a full WinAnsi embed is the
  design's choice, not a requirement.
- The alias `/Body` is `Object.sanitize_name/1` of the registered name, as
  `acro_form_font_alias/1` already does for standard fonts
  (`serialize.ex:781-782`).

## D. Appearance streams

### Decision: every widget gets `/AP /N`

`/NeedAppearances` is never written: `acro_form_entry/2`
(`serialize.ex:745-750`) loses the branch. `PDFA-2B 6.4.1-3` requires the flag
to be absent or false. `PDFA-2B 6.3.3-1` requires an appearance dictionary on
every annotation except zero-size ones, Popup and Link.

**The shape of `/AP`** follows `PDFA-2B 6.3.3-2` to `6.3.3-4`, which Tincture
then meets for every document, not only archival ones:

- **only `/N`**, no `/R` or `/D` (`6.3.3-2`);
- **for `/FT /Btn`** (checkbox, radio, push button), `/N` is a subdictionary
  of named states (`6.3.3-3`). The push button already writes a stream today
  (`serialize.ex:1348-1360`). That is examined in its own subsection below;
- **for every other field type**, `/N` is a stream (`6.3.3-4`).

### Text fields

**Single line.** The appearance is a form XObject the size of the widget
rectangle. Its content is marked as variable text and clipped to the rectangle
inset by 1 point:

```
/Tx BMC
q
1 1 198 22 re
W
n
BT
/F1 12 Tf
0 g
2 7.4 Td
(Ada Lovelace) Tj
ET
Q
EMC
```

The `/Tx BMC … EMC` bracketing follows ISO 32000-1 12.7.3.3 (**unverified**).
No veraPDF rule checks it, and the design keeps it because it costs nothing.

- **`/Q` quadding.** `:align` is `:left` (0), `:center` (1) or `:right` (2).
  It is written as `/Q` on the field, and applied in the appearance by
  offsetting `Td` with the value's width measured by `TextExtent.extent/4`
  (`lib/tincture/pdf/text_extent.ex`), the same measure a text link uses.
- **Vertical placement** centres the line between the font's ascent and
  descent.
- **Font size 0 (auto)**, for a single line, is the largest size that fits
  both:
  - the height: `(h - 2) / 1.15`, capped at 12;
  - the width: the measured value at that size must fit within `w - 4`.

  The 12-point cap and the 1.15 line factor are the design's choice. Viewers
  may compute auto size differently when they regenerate (**unverified**).
  The value written is the size Tincture computed. `/DA` keeps `0 Tf`, so an
  editing viewer still auto-sizes.

**Multiline** (`multiline: true`):

- **Wrapping.** The value is wrapped greedily to `w - 4` at spaces, and at
  explicit `\n`. The Knuth-Plass engine is not used: an editing viewer wraps
  greedily, and the generated appearance should look like what the user will
  see after editing.
- **Layout.** Lines start from the top inset. The leading is 1.15 × size.
- **Auto size** starts at 12 and steps down by 0.5 until the wrapped text fits
  the height, with a floor of 4. Below the floor the text is clipped.

**Password fields.** The appearance draws no text, whatever the value. The
value itself is still written as `/V`, which is the current behaviour. The
`@doc` says the value is readable by anyone who opens the file.

**Comb fields: out of 0.4.0.** No current option creates one: there is no
comb flag in `field_flags/2`. They need a `/MaxLen` cell layout, and nothing
in the release depends on them.

### Choice fields

**Combo box** (`dropdown: true`). The appearance is that of a single-line text
field showing the selected value, or nothing when there is none.

**List box** (`dropdown: false`):

- **Rows.** Options are drawn top to bottom, one per row, at the field's size.
  Auto size uses 12, capped by the height of one row.
- **The selected option** is drawn on a filled rectangle,
  `0.6 0.75 0.9 rg … re f`, with its text in black.
  - The colour is the design's choice, not a standard one.
  - The first visible option is the selected one when it would otherwise fall

### Signature fields

**Visible** (non-zero rectangle):

- `/N` is a stream.
- **Unsigned**, or signed without `:label`, the content is empty:
  `/BBox [0 0 w h]` and `/Length 0`. An empty stream is still an appearance,
  which is what `PDFA-2B 6.3.3-1` requires.
- **`:label`**, a new `signature_field/7` option, draws one line of text,
  left-aligned, laid out like a single-line text field: for example "Signed
  by A. Lovelace".
- No graphic or image is drawn. That is out of scope (section I).

**Invisible.** `signature_field/7` accepts `invisible: true`, which writes
`/Rect [0 0 0 0]` and no `/AP`.

- **PDF/A.** `PDFA-2B 6.3.3-1` exempts it: "the value of the Rect key
  consists of an array where value 1 is equal to value 3 and value 2 is equal
  to value 4".
- **PDF/UA.** Whether such a widget is "outside the crop box", and so exempt
  from `PDFUA-1 7.18.4-1`, depends on veraPDF's `isOutsideCropBox` for a
  degenerate rectangle at the origin. That is **unverified**. The design does
  not rely on it: an invisible signature is owned by a `Form` element like any
  other widget (section F).
- **`/F`.** It keeps `/F 4` (Print), as `PDFA-2B 6.3.2-2` requires print set
  and hidden clear.

The signature dictionary, the `/ByteRange` and the `/Contents` do not change
(`lib/tincture/pdf/sign.ex:55-143`).

### Checkbox, radio and push button

- **Checkbox and radio** are unchanged in output. They draw no text and use no
  font.
  - Their builders change from strings to operation lists, as section B
    requires.
  - Their appearance bytes are pinned by the existing tests, and must not
    move.
- **The push-button caption** stops writing an inline `/Helv` Type1
  dictionary (`serialize.ex:1374-1376`).
  - Its font resource comes from the shared pipeline: the field's `:font`,
    standard or embedded, named per stream.
  - With a standard font the caption bytes are equivalent, and the resource
    becomes `/F1` rather than `/Helv`. That change is listed in the CHANGELOG.

**The push button's `/N` breaks `PDFA-2B 6.3.3-3`.**

- **Today.** `push_button_appearance_object_body/1` (`serialize.ex:1348-1360`)
  writes one stream, so `/AP << /N 25 0 R >>` holds a stream.
- **The rule.** `6.3.3-3` requires a subdictionary for `/FT /Btn`.
- **Why it does not matter today.** Push buttons are refused under PDF/A
  anyway (section E), so no validated document carries one.
- **Decision.** The push button writes `/AP << /N << /Default 25 0 R >> >>`
  with `/AS /Default`, so the rule holds in every document.
  - The state name `/Default` is the design's choice.
  - This is the one change in 0.4.0 to an appearance that already exists.

### `/DA` and `/DR`

- **`/DA` is written only on text and choice fields**, the fields whose
  appearance a viewer regenerates from a value. Checkbox, radio, push button
  and signature fields stop carrying `/DA`. Today every widget has one
  (`serialize.ex:1178`). That `/DA` is not required on those fields is
  ISO 32000-1 12.7.3.3, **unverified**, so the change is held back if veraPDF
  reports otherwise on the corpus.
- **`/DR /Font`** lists exactly the fonts named by some field's `/DA`, under
  the alias used there. An embedded font appears as the simple dictionary of
  section C, and a standard font as today.
- **The AcroForm-level `/DA`** (`default_appearance_string/1`, `serialize.ex:767`)
  names the first text or choice field's font. It is omitted when there are
  none.
- **Consistency is a test.** For every widget with `/DA`, the font alias it
  names resolves in `/DR`, and the same font object is used by that widget's
  `/AP` stream resources.

### `/MK`, JavaScript and flattening

- **`/MK`: out.** It records border and background colours for a viewer to
  use when it regenerates an appearance. No conformance rule in the profiles
  read here requires it, and the generated appearances draw their own border
  through the existing `:border`.
- **JavaScript actions: out.**
  - `PDFA-2B 6.5.1-1` forbids JavaScript actions in PDF/A, and `6.4.1-1` and
    `6.4.1-2` forbid `/A` and `/AA` on widgets and fields.
  - So they could never appear in the archival half of the release.
  - Client-side validation is a separate feature with its own surface.
- **Flattening: out.**
  - It converts fields to page content, which removes the widgets and with
    them the `Form` elements of section F. That needs its own decision about
    what the structure tree becomes.
  - Generated appearances as form XObjects make it cheap later: placing an
    appearance on the page is `place_form_xobject` of section B.

### Tests

- **Per field type, single and multiline,** the appearance bytes are tested,
  including `/Q` quadding, auto size, wrapping and clipping.
- **The list-box selection** rectangle is tested.
- **The signature** gets three tests: an empty visible appearance, a labelled
  one, and an invisible one.
- **No document writes `/NeedAppearances`.**
- **The push button's `/N`** is a subdictionary.
- **The `/DA`/`/DR` consistency test** above.
- **The structure of `/AP`:** for every widget, `/AP` has only `/N`, a
  dictionary for `/Btn` and a stream otherwise. This is a local mirror of
  `PDFA-2B 6.3.3-2` to `6.3.3-4`.

### A `:form` structure element

- **Where.** `lib/tincture/pdf/structure.ex` gains `form: "Form"`.
- **Not a content element.** It must not join `@content_tags`
  (`structure.ex:60-80`), because it carries no marked content. 7.18.4-2
  requires that a `Form` without a Role attribute has exactly one child, the
  `/OBJR`, and an MCID would be a second.
- **Not a grouping element either.** It has no element kids.
- **A third kind: annotation-owning.** Its `/K` is the single `/OBJR`, written
  by the existing `/OBJR` path (`serialize.ex:647-654`).
- **No Role attribute.** Tincture never writes `/Role`, so 7.18.4-2's
  one-child condition always applies, and the design satisfies it by
  construction.

### Who owns which widget

**Options.**

1. **The caller opens it.** The field function must be called inside
   `tag(pdf, :form, fn …)`, as a link is called inside a `:link`.
2. **Automatic.** In a tagged document, each field call creates one `Form`
   element per widget, as a child of the innermost open structure element.
3. **An explicit option** naming the parent element.

**Decision: option 2.**

- **Why.**
  - 7.18.4-2 fixes the shape completely: one widget, one `Form`, nothing else
    inside. So there is nothing for the caller to choose, and a scope they
    must open adds only the chance to open it wrongly.
  - Links associate automatically for the same reason, stated at
    `lib/tincture/pdf.ex:905-909`: "opt-in is the wrong default for a rule the
    format requires".
  - The difference from links is that a link's element is the caller's (they
    choose `:link`), whereas a `Form` element has no content of its own to
    scope.
- **The mechanism.** Field creation calls the same association path that
  `PDF.add_link/4` uses (`pdf.ex:903`, `associate_annotation/2` at `910-916`),
  except that it appends a new `:form` child, which owns the widget's id, to
  the innermost open element. It does not attach the id to that element
  directly.
- **With no open element** in a tagged document, the widget is outside the
  structure. Export refuses it as a new violation, `:field_outside_structure`
  (clause 7.18.4), mirroring `:link_outside_structure`
  (`lib/tincture/pdf/accessibility.ex:149-150`). In an untagged document,
  nothing is created and nothing is checked, as for links.

**The radio group** is one field with N widgets (`serialize.ex:1080-1110`).

- It gets **N `Form` elements, one per button widget**, all children of the
  element that was open when `radio_group/4` was called, in button order. Each
  owns its kid widget.
- One `Form` with N `/OBJR` kids would break 7.18.4-2 without a Role
  attribute.
- Buttons on different pages are allowed (`:page` per button,
  `lib/tincture.ex:468`). Each `Form` element records its widget's page.

**Signature fields**, visible or invisible, get one `Form` element like any
other widget.

**`/StructParent`** is written on every owned widget. Its key is taken from
the same counter as link annotations (`serialize.ex:1036-1043`), and
`/ParentTree` maps it to the `Form` element (`parent_tree_body/4`,
`serialize.ex:596-630`). That is the existing mechanism, applied to widgets.
The only new part is the ownership described above.

### Bytes

A text field inside a `:section`, in a tagged document:

```
40 0 obj
<< /Type /StructElem /S /Form /P 38 0 R /Pg 3 0 R /K [<< /Type /OBJR /Obj 20 0 R >>] >>
endobj

20 0 obj
<< /Type /Annot /Subtype /Widget /FT /Tx /T (full_name) /TU (Your full name) /Rect [72 700 372 724] /P 3 0 R /F 4 /DA (/Body 0 Tf 0 g) /AP << /N 21 0 R >> /StructParent 2 >>

```

and in `/ParentTree`, `2 40 0 R`.

### `/TU` is required

`:tooltip` is already written as `/TU` (`tooltip_entry/1`, `serialize.ex:1239-1242`).

**Decision.** In a tagged document, every field must have a non-blank
`:tooltip`. Export refuses one without it, as a new violation:

```
rule: :field_without_description, clause: "7.18.1"
message: a text field "full_name" on page 1 has no tooltip. In a tagged
document every form field needs one: it is written as /TU, the name a screen
reader announces for the field. Pass tooltip: "..."
```

- **Why export time, and only in tagged documents.** This is the same reason
  that `:contents` on links is required only in a tagged document
  (`accessibility.ex:124`, `link_structure_test.exs:207`): whether a document
  is tagged is known only once tagging has happened.
- **Why `/TU` rather than `Alt`.** 7.18.1-3 also accepts an `Alt` on the
  enclosing structure element. Requiring `/TU` gives one rule rather than
  two, and `/TU` is also what a non-assistive viewer shows on hover.
- **The radio group.** It has one `/TU` on the parent field, since 7.18.1-3
  is a test on the field.
- **Language.** 7.2-25 is met by the catalog `/Lang` from `set_language/2`.
  Whether a tagged document without `set_language/2` is already refused is
  not established here. The tagged form example sets it.

Requiring `:tooltip` in untagged documents as well is an open question
below.

### `/Tabs /S`

**Fact.** It is written on **every page of a tagged document**, whether the
page has annotations or not (`serialize.ex:162-169`,
`tabs = if PDF.tagged?(pdf), do: " /Tabs /S", else: ""`). So pages with links
in a tagged document carry it today, and 7.18.3-1 holds for them.

**Decision for widgets: unchanged.**

- A tagged document with widgets has `/Tabs /S` on every page, so 7.18.3-1
  holds.
- An untagged document claims no PDF/UA, and keeps writing no `/Tabs`, so its
  bytes do not move.

### Tests

- **Parsing tests** in the style of `test/tincture/link_structure_test.exs`
  (which follows references rather than matching bytes). For a text field, a
  checkbox, a choice field, a three-button radio group and a signature:
  - each widget is owned by exactly one `/S /Form` element;
  - that element's `/K` is a single `/OBJR` naming the widget;
  - the widget carries `/StructParent`;
  - `/ParentTree` resolves it to the `Form`;
  - the `Form`'s parent is the element that was open.
- **Refusals:** `:field_without_description` and `:field_outside_structure`.
- **No-ops:** an untagged form gets no `Form` elements and no `/StructParent`.
- **Corpus coverage:**
  - `test/tincture/corpus_coverage_test.exs` loses the comment at lines 37–40.
  - `Form` joins the validated set once the tagged form example exists, and
    the test is updated so that it fails if no validated document emits
    `/S /Form`.

**Why the deprecations come first:**

- They are independent of everything else and are the smallest stage.
- Stage 2 rewrites the functions that W1 and W2 live in (`paint_open_path/4`
  reads the current page's operations; `warn_open_marked_content/2` reads
  them on page change). Making them errors first means stage 2 generalises
  the final code, not a warning path that is about to change.
- Last would also work, but it would leave a breaking change to land on top
  of the largest refactor in the release, where a regression is hardest to
  attribute.

**Why stage 2 is separate from stage 3.** Stage 2 is pure plumbing, and is
proved by byte-identity alone. Folding it into the font work would mean one
diff in which a byte change could come from either.

**Why 7 before 8.** The archival example validates appearances and fonts
without any new structure. When the tagged example then fails, the failure
is about structure.

## I. Out of scope

- **Footnote `Lbl` and `Link`** (the two PAC Quality warnings on `compliant.pdf`
  recorded in the ROADMAP, §1). This needs links to structure elements: there is no such link
  target today (`lib/tincture/pdf.ex:918-944`). That is unrelated to forms,
  and not a PDF/UA-1 requirement by veraPDF's profile, which has no rule for
  it.
- **Patterns** (ROADMAP item 5) and **soft masks on drawn content** (item 6).
  Section B keeps them possible, but builds neither.
- **Blend modes** (ROADMAP §5). They are unrelated to forms.
- **`/MK`, JavaScript actions and flattening.** See section D.
- **Comb fields and multi-select list boxes.** See section D.
- **Rotated form XObject placement** and **rotated widgets** (`/R` in `/MK`).
  No caller has asked for them, and `/MK` is out.
- **Editable fields with CFF (OpenType) fonts.** See section C.
- **Graphics in signature appearances.** An image or drawn signature in the
  appearance is a separate feature. `:label` covers the text case.
- **Rich text field values** (`/RV`). No current option produces them.
- **A second signature, counter-signing, timestamps and the PAdES
  `/ETSI.CAdES.detached` subfilter.** These need incremental updates or an
  HTTP client (ROADMAP §3, packaging: `tincture_tsa`).
- **XFA.** It is forbidden in PDF/A (`PDFA-2B 6.4.2-1`), and dynamic XFA in
  PDF/UA (`PDFUA-1 7.15-1`). It is not generated.
- **Corrections to existing documentation** unrelated to forms. They are
  handled separately.

## Questions this document cannot settle

1. **Simple-font `/DA` for editable fields** (section C). Restricting editable
   values to WinAnsi rests on viewer behaviour that is **unverified**. The
   alternatives:
   - (a) keep the WinAnsi restriction, as written;
   - (b) allow the Type0 dictionary in `/DR`, and test viewers by hand
     before the release;
   - (c) refuse embedded fonts on editable fields outside PDF/A.
2. **`:tooltip` outside tagged documents** (section F). Required only in
   tagged documents, as written, or required on every field? The second is
   breaking for untagged callers, and 0.4.0 is the version that can take it.
3. **Full embed for editable fields** (section C). It enlarges every editable
   form that uses an embedded font, often by hundreds of kB. Is that
   acceptable as the default, or should it be an option (`full_font: true`)
   with refusal as the default?
